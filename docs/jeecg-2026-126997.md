# CVE-2026-126997: JeecgBoot airag flow-run SSRF

## What is the JeecgBoot airag flow-run SSRF?

**CVE-2026-126997** is an unauthenticated server-side request forgery in
JeecgBoot's airag flow engine: on a default installation through 3.9.6 (and the
current main line), one anonymous `POST /airag/flow/run` for the seeded flow
makes the server issue an HTTP request whose scheme, host and port are
chosen by the caller through the `Host` and `X-Forwarded-Scheme` request headers.

The controller `org/jeecg/modules/airag/flow/c/a.class` is annotated
`@IgnoreAuth` and loads a flow from the database by id. The shipped seed dump
contains the flow `1900029596154232833` ("示例_Http节点"), whose first HTTP
node posts to `{{domainURL}}/test/jeecgDemo/add`. `CommonUtils.getBaseUrl`
resolves `{{domainURL}}` from the request `Host` header; the
`X_GATEWAY_BASE_PATH` header is an alternate branch that upstream code partially
validates. The node sends the request with `RestTemplate.exchange`. The advisory
demonstrates the response being reflected in the SSE stream and a
caller-supplied `X-Access-Token` being forwarded to the chosen destination.

## Which JeecgBoot versions are affected by CVE-2026-126997?

**Affected:** the upstream `v3.8.0last` tag through 3.9.5 and the current
main line (NVD lists 3.9.0 through 3.9.6; no fixed release existed at
disclosure, so treat 3.9.6 as affected too; the plain `v3.8.0` tag is not
affected because it lacks `@IgnoreAuth`). The advisory recommends removing
`@IgnoreAuth`, resolving the base URL from server-side configuration and
enforcing a host allow-list.

## How do I remediate CVE-2026-126997?

**Remove `@IgnoreAuth` from `/airag/flow/run` and require an authenticated
caller with an explicit flow-execution permission.** Do not resolve
`{{domainURL}}` from the request `Host` or `X_GATEWAY_BASE_PATH`; use a
server-side configured base URL and enforce a scheme/host/port allow-list that
blocks loopback, link-local and private ranges before `RestTemplate.exchange`.

In the interim, until the code change is applied:

- Delete or disable the seeded sample flow `1900029596154232833`.
- Block or answer `/airag/flow/run` at a reverse proxy for unauthenticated
  callers.

After applying the change:

- Review airag flow definitions for other request-derived URLs.
- Review airag and outbound-request logs and rotate any credential the server
  could reach.

## How does the detector confirm CVE-2026-126997?

1. Attribute JeecgBoot from anonymous
   `GET /jeecg-boot/sys/version/app3version` (or
   `GET /sys/version/app3version` without the context prefix) with the
   product app-version schema.
2. Send one anonymous `POST /jeecg-boot/airag/flow/run` with
   `Content-Type: application/json`, `Host: 127.0.0.1:1`,
   `X-Forwarded-Scheme: http`, and the body
   `{"flowId":"1900029596154232833","inputParams":{"content":"ostorlab-ssrf-probe"}}`.
3. Require the SSE/JSON response to contain the exact caller-derived URL
   `http://127.0.0.1:1/jeecg-boot/test/jeecgDemo/add` **and** the
   `I/O error on POST request for` transport marker and `Connection refused`.
   A timeout is inconclusive. The flow's POST node is
   refused before it can create a demo record; the target contacts no live
   service.

A deployment with the seeded flow removed answers `流程不存在`; a build that
requires authentication answers 401/403; a non-JeecgBoot server fails
attribution. None of those produces a finding.

## Is the check safe to run?

- Anonymous: no credential, token, signature or cookie is sent.
- Loopback only: `Host: 127.0.0.1:1`; the flow's POST is refused, so no live
  service is contacted and no demo record is created.
- No external destination, cloud metadata, file, command or configuration
  endpoint is requested.
- The flow's response is bounded at 64 KiB; a larger response is
  inconclusive.
- The check confirms the SSRF dispatch. It does not read an internal response
  or exercise the `X_GATEWAY_BASE_PATH` branch.

## What are the detection limits?

- Plain HTTP only: a loopback HTTPS self-proxy would face the server's own
  certificate validation.
- Requires the default seeded flow and the default context path; a deployment
  that deleted the flow, changed its id, or requires authentication is not
  reported.
- A reverse proxy that rewrites `Host` (and does not forward the alternate
  `X_GATEWAY_BASE_PATH` branch) produces no finding.
- The `I/O error on POST request for` marker is the English JDK/Spring
  message; a localized JVM could suppress the finding (inconclusive, not a
  clean negative).
- The check does not exercise the `X_GATEWAY_BASE_PATH` branch or the
  `X-Access-Token` forwarding; those remain advisory-demonstrated impacts.
- The detector confirms the dispatch, not a successful internal response read.

## How do I run this detector?

This detector runs automatically during an `oxo` scan of a responding
JeecgBoot instance; no flag is required.

## Generic handoff (not closed by this module)

The reusable pattern is an unauthenticated flow/automation engine that binds
the inbound request into an execution context and resolves a URL placeholder
from a caller-controlled `Host` (or gateway base-path) header before an
outbound HTTP call. It belongs to the General Rule Creator's open
trusted-Host / self-referential URL-fetch handoffs; this CVE module does not
claim generic coverage.
