# CVE-2026-134748: Members Private Site login-path authorization bypass

**[CVE-2026-134748](https://nvd.nist.gov/vuln/detail/CVE-2026-134748) is an
unauthenticated Private Site mode bypass** in the Members WordPress plugin by
MemberPress (CWE-288, CVSS 3.1 5.3, CVSS 4.0 6.9). In releases 3.2.28 through
3.3.1, `members_is_login_page_request()` in `inc/functions-private-site.php`
exempted the login page by request path alone.

On a site whose login URL is a front-end page, a request that keeps the login
path while supplying a `pagename` query variable makes the WordPress main query
resolve to another published page. The path-only exemption still lets that page
render for a logged-out visitor. The same exemption covered the POST `page_id`
variant and the loop-free sitemap, robots, feed and trackback routes.

**Affected:** Members 3.2.28 through 3.3.1
([GHSA-4jhr-qq5j-w7qg](https://github.com/caseproof/members/security/advisories/GHSA-4jhr-qq5j-w7qg))

**Fixed:** Members 3.3.2
([fix commit b439600](https://github.com/caseproof/members/commit/b43960048e65029446184ee372e9a782efea4a07))

**Severity:** CVSS 3.1 5.3 (Medium) —
`AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N`; CVSS 4.0 6.9
(`AV:N/AC:L/AT:N/PR:N/UI:N/VC:L/VI:N/VA:N/SC:N/SI:N/SA:N`)

The bypass needs two deployment conditions: Private Site mode must be enabled,
and the site's login URL must be served from a front-end page rather than the
default `/wp-login.php`. Plugins such as WP Ghost or WPS Hide Login, or a
custom `login_url` filter, produce that shape. A site with at least one
published non-auth page lets the detector confirm that the page actually
renders; a site with no such page is inconclusive rather than reported.

## How does the detector verify the bypass?

1. `GET /wp-content/plugins/members/readme.txt` must return the exact heading
   `=== Members - Membership & User Role Editor Plugin ===` and a single
   `Stable tag` in 3.2.28 through 3.3.1. A missing readme, a different heading
   or a release outside the interval is not attributed.
2. The login document must look like WordPress: it carries `wp-content/` or
   `wp-includes/` asset markers and either a WordPress page id or a recognizable
   login form. Private REST mode is accepted, because it is a supported
   configuration.
3. `GET /` must redirect to a front-end login path. The login path alone must
   return HTTP 200 with a WordPress page or login form, and a random non-login
   path must also redirect to that login path. A site with Private Site mode
   off, or with the default `/wp-login.php` login URL, fails this step.
4. Page candidates come from the anonymous `/wp-json/wp/v2/pages` list when it
   is public, or from the shipped `privacy-policy` and `sample-page` slugs when
   the private REST option is on. The login, registration and password pages
   are excluded.
5. `GET <login-path>?pagename=<slug>` must return HTTP 200 with the candidate's
   `page-id-<id>` body class and a content marker, and must not be the login
   page's own id. A fixed 3.3.2 site redirects the same request to the login
   path. The detector retains only the status code, the page id and the login
   page id; it does not retain the page title, body or any user data.

## What does a positive finding claim?

The finding confirms the Private Site login-path bypass: the login path with a
`pagename` query rendered a different published page anonymously, while the
login path alone rendered the login page and a random non-login path still
redirected to login. It does not claim that a specific protected post, user
record or credential was read.

## What does the detector miss?

**Not reported by design (true negatives):** Private Site mode off, a fixed
3.3.2 release and a default `/wp-login.php` login URL do not produce the
differential and are correctly not reported.

**Coverage gaps (inconclusive):**

- A site with no published non-auth page has nothing for the probe to render;
  it is a coverage limitation, not a clean negative.
- A login page served from a virtual path with no WordPress page markers and
  no recognizable login form is not attributed.
- A reverse proxy that normalizes or blocks the `pagename` query, or that
  strips the plugin readme, prevents the probe.
- A site whose login URL is a front-end page but whose private-site mode is
  provided by another plugin is not attributed to Members without the readme.
- Network errors, timeouts, redirects, oversized bodies and malformed JSON are
  inconclusive and produce no finding; a missing finding is not proof that the
  bypass is absent.

## How do I run the check?

```sh
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-134748"]' ip 10.0.0.10
```

The equivalent manual differential on the same origin is:

```sh
curl -i 'http://10.0.0.10/'
curl -i 'http://10.0.0.10/login/'
curl -i 'http://10.0.0.10/login/?pagename=privacy-policy'
curl -i 'http://10.0.0.10/asteroid-does-not-exist'
```

A vulnerable 3.3.1 site redirects `/` and the random path to `/login/`, renders
the login page at `/login/`, and renders the privacy page at
`/login/?pagename=privacy-policy`. A fixed 3.3.2 site redirects that last
request to `/login/` as well.

## How do I fix CVE-2026-134748?

Upgrade the Members plugin to 3.3.2 or later. The fix confirms that the main
query resolved to the login page and that the loop holds nothing else before
applying the login exemption, and it refuses 404s, sitemaps, robots, feeds and
trackbacks. If the plugin cannot be updated, turn off Private Site mode and
enforce the restriction at the web server or an authenticated reverse proxy.

Sites that moved the login URL to a front-end page with WP Ghost, WPS Hide
Login or a custom `login_url` filter must be updated, because the bypass needs
that front-end login path. Review web-server logs for anonymous requests to
the login path carrying `pagename` or `page_id` query variables, and treat
published content reachable that way as potentially disclosed.

## How was the detector validated?

The fixtures are WordPress 7.1.5 with the real Members 3.3.1 and 3.3.2 release
zips, MariaDB 11.8.9, PHP 8.4.28 and a small `mu-plugin` that moves the login
URL to a front-end page, matching the WP Ghost/WPS Hide Login shape. An
independent stdlib `http.client` oracle established ground truth without
importing the detector, and the registered detector ran from a separate client
process.

| Fixture | Oracle | Detector | Result |
| --- | --- | --- | --- |
| Members 3.3.1, `/login/`, private site on, public REST | vulnerable | 1 finding | TP |
| Members 3.3.1, `/login/`, private REST on | vulnerable | 1 finding | TP |
| Members 3.3.1, `/welcome/`, `about` page, private site on | vulnerable | 1 finding | TP |
| Members 3.3.2 fixed, private site on | fixed | no finding | TN |
| Members 3.3.1, private site off | not vulnerable | no finding | TN |
| Members 3.3.1, default `/wp-login.php` login URL | not vulnerable | no finding | TN |
| Members 3.3.1, readme missing (non-Members attribution) | not Members | no finding | TN |
| Members 3.3.2 fixed with a stale 3.3.1 readme | fixed | no finding | TN |
| Members 3.3.1, no published non-auth page | inconclusive | no finding | inconclusive |

**TP 3 / TN 5 / FP 0 / FN 0 / inconclusive 1** (9 cases). These are curated
fixture results, not a production false-positive rate. The fixture build,
oracle, detector client and raw results are under
`artifacts/asteroid/2026-11-22-members-private-site-bypass/` in the shared
memory.
