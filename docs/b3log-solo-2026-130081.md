# B3log Solo CVE-2026-130081 article view-password disclosure

**CVE-2026-130081** is an unauthenticated information disclosure in B3log
Solo, the Java blog engine released by the B3log project and distributed as
Solo. Versions through 4.4.0 leave the plaintext `articleViewPwd` field of
published articles in the public `GET /articles` JSON response (CWE-201, CVSS 3.1 7.5
`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`, CVSS 4.0 8.7).

The field is the password used to gate a protected article's content. An
anonymous visitor can read the view password of every listed article and
then submit it to open the protected content. The vulnerable handler is
`ArticleProcessor.getArticlesByPage`; the field survives because
`DataModelService.setArticleExProperties` does not remove it from the public
article model.

No fixed release existed at disclosure. Upstream fix commit `46308431`
removes the field in `DataModelService.setArticleExProperties`.

## How does the detector verify the disclosure?

1. Read `GET /` and require an HTML home page with the shared B3log
   copyright header (`<meta name="copyright" content="B3log">`). B3log Solo
   and the Bolo fork (`adlered/bolo-solo`) share that header, so the reader
   also rejects the fork's own skin path (`/skins/bolo`) and footer link
   (`adlered/bolo-solo`); article text that merely mentions `bolo-solo` is not
   excluded. A non-B3log site stops here.
2. Read `GET /articles` and require:
   - HTTP 200 with an `application/json` content type;
   - the B3log Solo `code`/`rslts` envelope with `code == 0`;
   - an `rslts.pagination` object with an integer `paginationPageCount`;
   - an `rslts.articles` array whose first row has string `oId`,
     `articleTitle`, `articlePermalink` and `articleViewPwd` fields.

   The Bolo fork's `sc`/`rslts` envelope is rejected as a lookalike.
3. Report only when at least one listed article has a non-empty
   `articleViewPwd` string and a non-empty string `oId`. An empty password is
   not a disclosure.
4. Follow the public `?p=N` paging for at most five pages, so a protected
   article on a later page is found without an unbounded walk.

Only anonymous `GET` requests are sent. The detector never submits a
password, requests a protected article page, sends a credential or cookie, or
changes state. The leaked password value is never copied into the finding;
the evidence names the article `oId` and the page only.

## What does a positive finding claim?

The finding confirms that the anonymous `/articles` response returned a
non-empty plaintext `articleViewPwd` for a published article. It does not
claim that the protected body was read: the detector did not submit the
password or request the protected article page. A fixed build that removes
`articleViewPwd` from the response (upstream fix commit `46308431`), or a
deployment that protects `GET /articles`, is not reported.

## What does the detector miss?

- A B3log Solo site whose custom theme removes the shared B3log copyright
  header is not attributed. That is a false negative, not a false positive.
- A protected article on page six or later is not reached because the walk is
  bounded at five pages.
- A site that returns a non-200 home page (for example a canonical-host
  redirect) is not attributed; redirects are not followed.
- A deployment that protects `/articles` with a 401/403 is not reported even
  if a protected article exists, because the anonymous disclosure is not
  observable.
- Network errors, timeouts, truncated or oversized bodies and malformed JSON
  are inconclusive; a missing finding is not proof that the target is
  protected.

## Reproduction

The validation artifact
(`artifacts/asteroid/2026-11-17-b3log-solo-articles-password/`) contains the
oracle, adapter, cases, benign lookalikes, fixture-init source and the fixed
patch. The two vulnerable fixtures are real upstream releases:

```shell
# v4.4.0 and v4.3.1 release zips from
# https://github.com/88250/solo/releases
unzip solo-v4.4.0.zip -d solo440
unzip solo-v4.3.1.zip -d solo431
# For each tree, configure local.properties with runtimeDatabase=H2 and
# jdbc.URL=jdbc:h2:<fixture>/data/db;MODE=MYSQL, set serverPort=18090 for
# v4.4.0 (18091 for v4.3.1), seed once with fixture_init.java (server
# stopped), then start the server:
java -cp "lib/*:." org.b3log.solo.Server \
  --listen_port 18090 --server_host 127.0.0.1 --server_port 18090
# The v4.3.1 fixture follows the same steps on port 18091. The fixed control
# is the v4.4.0 tree with fixed_data_model.patch compiled over the release
# class path.
```

Run the independent oracle and the registered detector from a separate
client:

```shell
python3 oracle.py --url http://127.0.0.1:18090
python3 adapter.py --url http://127.0.0.1:18090
```

For the full matrix, run `run_cases.py` from the vulnerability-rule-authoring
skill (`skills/vulnerability-rule-authoring/scripts/run_cases.py`) with
`--manifest cases.json --output validation.json`; `oracle.py`, `adapter.py`
and `cases.json` are the three inputs it invokes. `adapter.py` imports the
detector from the `agent_asteroid` checkout configured at its `REPO`
constant.

Run the focused suites and the full repository suite:

```shell
python3 -m pytest \
  tests/exploits/b3log_solo_articles_password_test.py \
  tests/exploits/cve_2026_130081_test.py \
  tests/exploits/bolo_articles_password_test.py \
  tests/exploits/cve_2026_129493_test.py \
  tests/exploits_registry_test.py tests/definitions_test.py \
  tests/asteroid_agent_test.py -q
python3 -m pytest -m 'not docker' -q
```

Run these with the repository's dependency set installed (the CI image).

Run the detector in a standard scan:

```shell
oxo scan run --install --agent agent/ostorlab/asteroid ip 8.8.8.8
```

Filter it to this detector with the `custom_cve_list` scanner setting:

```shell
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-130081"]' ip 8.8.8.8
```

The detector ships as part of the Asteroid agent and uses only anonymous
HTTP(S) requests.

## Generic path (not closed by this detector)

An unauthenticated article-list API that serializes an access-control secret
(the article view password) is the same reusable weakness as the existing
public-API-serializer-credentials handoff and the Bolo CVE-2026-129493
detector. The General Rule Creator owns the generic discovery and probe; this
CVE module does not claim generic coverage.
