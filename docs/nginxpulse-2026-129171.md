# NginxPulse CVE-2026-129171 unauthenticated SQL injection

**CVE-2026-129171 is an unauthenticated SQL injection** in NginxPulse's
`/api/stats/:type` endpoint. The handler interpolates the caller-supplied
website `id` into a quoted PostgreSQL table identifier
(`"<id>_agg_daily"`) and, for the `location` stats type, the caller-supplied
`locationType` into a column expression. No value is validated before the
query is built, and the database error is returned to the caller.

**Affected:** NginxPulse 1.5.0 through 1.6.25
**Fixed:** 1.6.26 (commit `f9416bea`)
**Severity:** CVSS 3.1 9.8 (Critical) — `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`; CVSS 4.0 9.3; CWE-89

An anonymous caller can close the quoted identifier, append SQL and use the
reflected error as an error-based read primitive. The public report reads
`/etc/passwd` through `pg_read_file`; the official deployment runs the
application against a PostgreSQL superuser, so the same primitive also
reaches server file read/write functions and `session_preload_libraries`
code execution.

## How does the detector verify the injection?

1. `GET /` must serve the NginxPulse SPA shell
   (`<title>NginxPulse - Nginx访问统计</title>`). The SPA fallback answers a
   client route with the shell and a `404` status, so the marker and the HTML
   content type are the evidence, not the status code.
2. `GET /api/version` must return the anonymous version document with a
   `v1.6.25`-shaped `version` and a string `git_commit`.
3. `GET /api/websites` must advertise at least one public website whose `id`
   is a plain `[A-Za-z0-9_]` token. This is the same list the console uses; it
   is not a credential.
4. `GET /api/stats/overall?timeRange=7d&id=<public id>` must return HTTP 200
   with the normal aggregate counters, proving the selected site is live.
5. The same request with the id
   `<public id>_agg_daily" JOIN (SELECT 1) z ON 1=(CAST('ostorlab-nginxpulse-probe' AS int)) --`
   must return HTTP 500 with the PostgreSQL error
   `invalid input syntax for type integer: "ostorlab-nginxpulse-probe"`
   (`SQLSTATE 22P02`). The error names the fixed literal, proving the website
   id is concatenated into the SQL identifier and the injected expression
   executed.

A fixed 1.6.26 server validates the website id and answers HTTP 400
(`站点不存在`) before the query runs; it also restricts `locationType` and
replaces the reflected database error with a generic message. An access-key
deployment answers 401, a site without parsed logs fails the baseline step,
and a lookalike that returns counters without the cast error is not reported.

The probe sends anonymous GETs only. It reads no row, file or configuration
value and writes nothing: only the database's own error text for a fixed
literal is retained. It sends no credential, access key, cookie or mutation.
The advisory's file read/write and code-execution impact is **not** exercised
or claimed.

## What does the detector miss?

- A deployment whose public website list is empty, or whose selected site has
  no aggregated tables yet, fails the baseline step and is inconclusive.
- An access-key-protected console answers 401 and is not reported, even
  though the injection exists behind the key.
- A deployment that hides the database error without adding the id/location
  validation returns a generic 500 and is not reported; the validation is the
  security fix, and the error is the observable.
- A reverse proxy that rewrites `/api/stats` or a deployment under a path
  prefix is not probed.
- Network errors, timeouts, truncated or oversized responses and unsupported
  schemes are inconclusive; a missing finding is not proof that the injection
  is absent.

## How to reproduce and remediate

Probe the endpoint yourself:

```sh
# 1. Read a public website id.
websites=$(curl -sS 'http://<target>/api/websites')
id=$(printf '%s' "$websites" | python3 -c 'import json,sys; print(json.load(sys.stdin)["websites"][0]["id"])')

# 2. Baseline.
curl -sS -G 'http://<target>/api/stats/overall' \
  --data-urlencode 'timeRange=7d' --data-urlencode "id=$id"

# 3. Fixed-literal cast probe (no row or file is read).
curl -sS -G 'http://<target>/api/stats/overall' \
  --data-urlencode 'timeRange=7d' \
  --data-urlencode "id=${id}_agg_daily\" JOIN (SELECT 1) z ON 1=(CAST('ostorlab-nginxpulse-probe' AS int)) --"
```

A vulnerable 1.6.25 server answers the third request with HTTP 500 and
`invalid input syntax for type integer: "ostorlab-nginxpulse-probe"`; a fixed
1.6.26 server answers HTTP 400 `站点不存在`.

Upgrade to 1.6.26 or later. Enable the access-key feature, restrict the
console to trusted networks, and run the application against a dedicated
ordinary PostgreSQL role without `SUPERUSER`, `CREATEDB`, `CREATEROLE`,
`REPLICATION`, `BYPASSRLS` or membership in `pg_read_server_files`,
`pg_write_server_files` or `pg_execute_server_program`. If an earlier build
was exposed, review database and web logs for injected `id`/`locationType`
values, treat the database credentials and any server file readable by that
role as potentially disclosed, rotate the credentials and check for
unexpected file changes. For the agent-side summary, run
`oxo vulnz describe -v CVE-2026-129171`.

## How do I run this detector?

The detector runs automatically during an `oxo` scan of a responding
NginxPulse instance; no flag is required. To restrict a scan to this CVE:

```sh
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-129171"]' url http://<target>
```

## Validation

The registered `CVE2026129171Exploit` was exercised from a separate network
client against real upstream Linux releases on loopback, with an independent
stdlib `http.client` oracle that never imports the detector:

| Fixture | Oracle | Detector | Result |
| --- | --- | --- | --- |
| NginxPulse v1.6.25 (vulnerable, upper bound) | injection 500 + cast error | 1 finding | TP |
| NginxPulse v1.6.24 (vulnerable variant) | injection 500 + cast error | 1 finding | TP |
| NginxPulse v1.6.26 (fixed) | injection 400 `站点不存在` | no finding | TN |
| version-only lookalike (NginxPulse shell/version, no cast error) | injection 200 | no finding | TN |
| other-product lookalike (different title/version) | no NginxPulse marker | no finding | TN |

**TP 2 / TN 3 / FP 0 / FN 0 / inconclusive 0** on the real-fixture matrix.
The focused mocked suite covers a fixed `locationType` rejection, a generic
hidden error, a missing marker, an unsafe website id, an access-key 401, a
transport failure, a redirect, an oversized body and a direct `check()` call
on a lookalike. Curated fixture results are not a production false-positive
rate.

## Generic handoff (not closed by this module)

The reusable pattern — a caller-controlled value used as a SQL identifier in
a query builder whose database error is reflected to an unauthenticated
caller, and the error-based boolean/cast differential used to confirm it — is
recorded as a handoff to the General Rule Creator. This CVE module does not
claim generic SQL-injection coverage.
