# MyMangaDB CVE-2026-77295 unauthenticated database export

**CVE-2026-77295** is an unauthenticated information disclosure in MyMangaDB,
a self-hosted manga collection manager. Through 2.7.1 the FastAPI backend
mounts `GET /api/v1/database/export` and `POST /api/v1/database/import` on a
router with no authentication dependency at all (CWE-200, GitHub advisory
severity high, CVSS 4.0 8.7
`AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:N/VA:N/SC:N/SI:N/SA:N`).

The export handler copies the live SQLite database and every stored cover
image into a ZIP and returns it to the caller. The database contains the
`users` table with `hashed_password` values, so any client that can reach the
backend can download the complete account list and every library item, then
attack the password hashes offline. The import route is the state-changing
sibling: an anonymous caller could replace the database and images.

Release **2.7.2** (commit
`2ad34ea785c01d096b38a01420d56fc5a1078db4`) adds
`Depends(deps.get_current_active_superuser)` to both routes, so an anonymous
request answers 401.

The vulnerable code is the `database.py` router in `backend/app/api/v1/endpoints/`:
at tag `v2.7.1` it imports `APIRouter, File, HTTPException, UploadFile` and
never imports or applies `Depends`. `export_database()` copies `DATABASE_PATH`
into a temporary `.db`, gathers every file under `IMAGE_PATH` into a
`ZIP_DEFLATED` archive, and streams it back with
`Content-Disposition: attachment; filename="mangadb_export.zip"`.

## How does the detector verify the disclosure?

1. Read `GET /` and require the backend root document exactly
   `{"message":"Welcome to the Manga API"}`.
2. Read `GET /api/v1/settings/getAll` and require a JSON object with
   non-empty string `database_path` and `image_path` fields. The settings
   route is unauthenticated in both the vulnerable and the fixed release, so
   it corroborates the product without depending on the vulnerable handler.
3. Send one anonymous `GET /api/v1/database/export` with
   `Range: bytes=0-32767` and read at most 64 KiB from the response stream.
   Require HTTP 200 or 206, a `Content-Type` containing `zip`, a first local
   ZIP entry whose name ends in `.db`, and that entry's data beginning
   with the SQLite magic signature: `SQLite format 3` followed by a NUL
   byte (`\x00`), 16 bytes in total.
4. Never retain or emit a database row, password hash, image or later archive
   member. The finding names the export route, the HTTP status and the
   database entry name only.

Only anonymous `GET` requests are sent. The detector does not send a
credential or cookie, does not submit a body, follows no redirect, and never
touches the import route.

## What does a positive finding claim?

The finding confirms that the anonymous export route returned a ZIP whose
first member is a live SQLite database. It does not claim that any user row,
password hash or image was read, and it does not call the deployment
"pre-2.7.2": a custom route or a proxy decision can produce the same exposure
on another release. A deployment that requires authentication, a deployment
whose export contains no database, and a proxy that answers a challenge or a
non-ZIP body are not reported.

## What does the detector miss?

- A separate frontend host (`VITE_API_URL` pointing at another origin) is not
  covered: the probe runs against the scanned origin's own `/api/v1` paths.
  Only the backend host (port `8000` in the official compose) is attributed.
- A customized `DATABASE_PATH` whose basename does not end in `.db` is not
  recognised as the database entry, even though the export still discloses it.
- A deployment that removes `/api/v1/settings/getAll` or returns a different
  root document is not attributed.
- A build that answers 401/403 for the export, a deployment that serves an
  empty archive, and a reverse proxy that answers an HTML challenge are not
  reported; the absence of a finding is not proof that the target is patched.
- Network errors, timeouts and responses larger than the bounded prefix are
  inconclusive.

## What operational impact does the probe have on the target?

The upstream handler builds the complete temporary archive before it starts
streaming. The `Range` request bounds only what the scanner reads; a scan of a
very large library makes the instance write a full database-plus-images ZIP to
its temporary directory. This is the handler's own behaviour, not additional
state introduced by the probe.

## How do I remediate?

Upgrade to MyMangaDB 2.7.2 or later. If an upgrade is not immediately
possible, require authentication in front of the backend (or restrict it to
the frontend network) and deny `GET /api/v1/database/export` to anonymous
clients. Treat every password hash and stored image as potentially disclosed:
force password resets, review the `users` table for unexpected administrator
accounts, and rotate any credential stored in the database.

## How was the detector validated?

The real upstream tags `v2.7.0`, `v2.7.1` and `v2.7.2` were checked out and
served as independent FastAPI `uvicorn` processes on loopback with isolated
`HOME` directories, so each fixture creates its own SQLite database. An
independent stdlib `http.client` oracle that never imports the detector
fetched the attribution documents and the export archive, opened the archive
with `zipfile`, and established whether the first member is a `.db` entry with
the SQLite header. The registered `CVE202677295Exploit` ran from a separate
client process.
