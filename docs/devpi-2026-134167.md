# CVE-2026-134167: devpi-web unauthenticated documentation path traversal

**[CVE-2026-134167](https://github.com/CVEProject/cvelistV5/blob/main/cves/2026/134xxx/CVE-2026-134167.json) is an unauthenticated arbitrary file read** in the devpi-web
`+doc` documentation route (CWE-22, CVSS 3.1 7.5, CVSS 4.0 8.7). Before 5.2.0
`docs_file_exists` and `docs_file_path` in `web/devpi_web/doczip.py` join the
caller-supplied `relpath` to the unpacked documentation directory without
normalizing or confining it. Encoded `..` segments (`%2e%2e`) or a leading `//`
escape the directory, and the unauthenticated route returns any file readable
by the devpi server process, including the keyfs SQLite database that holds
user password hashes and token identifiers.

**Affected:** devpi-web releases before 5.2.0 ([GHSA-w72q-5vww-p2rh](https://github.com/devpi/devpi/security/advisories/GHSA-w72q-5vww-p2rh))

**Fixed:** devpi-web 5.2.0 ([fix commit 680fca1](https://github.com/devpi/devpi/commit/680fca1607840905dab6c54059b65ba326f46850)).
devpi-server 6.21.0 ships the matching server-side changes.

**Severity:** CVSS 3.1 7.5 (High) — `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`;
CVSS 4.0 8.7 (`AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:N/VA:N/SC:N/SI:N/SA:N`)

Deployments that unpack project documentation are affected. A doczip is a
project version’s documentation archive. The default setting unpacks it
for serving through the documentation route.

## How does the detector verify the traversal?

1. `GET /` must return the devpi landing document: an exact
   `<title>devpi</title>` element, the `devpi-web-<release>` footer and the
   `+static-<release>/` asset prefix. The devpi-web release must be below
   5.2.0.
2. The anonymous JSON root (`Accept: application/json`) must list a stage
   index, and that index's config must list a project whose
   `/{user}/{index}/{project}/latest/+doc/index.html` documentation control
   renders with HTTP 200.
3. The same control path followed by the percent-encoded traversal
   `%2e%2e/%2e%2e/%2e%2e/%2e%2e/%2e%2e/.nodeinfo` must answer HTTP 200 with
   the devpi `.nodeinfo` JSON shape (`role` and a 32-hex `uuid`). Five parent
   directories reach the devpi server directory from
   `<serverdir>/<user>/<index>/<project>/<version>/+doc`.
4. The same five-level path naming a missing file must answer HTTP 404, so a
   catch-all server that serves any path is not reported.

The check reads only devpi's own non-sensitive `.nodeinfo` node identity. It
never requests the keyfs database, password hashes, tokens, uploaded package
data or configuration values, and it changes no state. A fixed 5.2.0 server
answers HTTP 400 to the encoded path.

## What does a positive finding claim?

The finding confirms the unauthenticated path traversal: the encoded dot
segments escaped the documentation directory and the server returned its
`.nodeinfo` file while the same path naming a missing file returned 404. It
does not claim that the keyfs database or any credential was read; that part of
the advisory's impact was deliberately not exercised.

## What does the detector miss?

- A deployment whose projects have no doczip has no reachable `+doc` entry and
  is not reported. This is a coverage limitation, not a clean negative.
- A deployment started with `--keep-docs-packed` reads documentation from the
  doczip archive and does not expose the unpacked-path traversal; it is not
  reported because it is not exploitable in that configuration.
- A reverse proxy that normalizes dot segments, collapses duplicate slashes or
  blocks the `+doc` route prevents both the finding and the underlying exploit
  even when the backend is vulnerable.
- A deployment that strips the `+static-<release>/` prefix and the
  `devpi-web-<release>` footer cannot be attributed or version-checked.
- A deployment mounted under a path prefix is not probed; the check uses the
  origin's standard paths.
- Network errors, timeouts, redirects, oversized bodies and malformed JSON are
  inconclusive and produce no finding; a missing finding is not proof that the
  traversal is absent.

## How do I run the check?

```sh
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-134167"]' ip 10.0.0.10
```

The equivalent manual differential on the same origin is:

```sh
curl -i 'http://<target>:3141/alice/dev/pkg1/latest/+doc/index.html'
curl -i --path-as-is \
  'http://<target>:3141/alice/dev/pkg1/latest/+doc/%2e%2e/%2e%2e/%2e%2e/%2e%2e/%2e%2e/.nodeinfo'
curl -i --path-as-is \
  'http://<target>:3141/alice/dev/pkg1/latest/+doc/%2e%2e/%2e%2e/%2e%2e/%2e%2e/%2e%2e/.nodeinfo-ostorlab-missing'
```

| Request | Vulnerable | Fixed 5.2.0 |
| --- | --- | --- |
| `+doc/index.html` | `200` documentation | `200` documentation |
| `.../%2e%2e/.../.nodeinfo` | `200` `{"role": ..., "uuid": ...}` | `400` Bad Request |
| `.../%2e%2e/.../.nodeinfo-ostorlab-missing` | `404` | `400` |

Run the three commands against the same origin and compare the status codes
with the table above; substitute an existing project/version from the target's
index.

## How do I fix CVE-2026-134167?

Upgrade devpi-web to 5.2.0 or later and restart the devpi-server process. If an
upgrade cannot be applied immediately, serve the devpi instance behind a
reverse proxy that collapses duplicate slashes and normalizes dot segments in
the request path, and restrict the HTTP endpoint to trusted clients. If an
affected deployment was reachable by untrusted clients, treat the keyfs
database as exposed: rotate every devpi user password and token, and review
the server access log for `+doc` requests containing `%2e%2e` or a doubled
slash.
