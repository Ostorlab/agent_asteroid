# Meetily CVE-2026-127286 unauthenticated self-hosted backend

**CVE-2026-127286 is an unauthenticated backend exposure** in Meetily's
legacy client-server architecture. The FastAPI backend at
`backend/app/main.py` mounts every route without an authentication dependency,
binds `uvicorn` to `0.0.0.0`, and the documented Docker Compose deployment
publishes the backend port (5167). Any network client that can reach that port
can read the meeting list and transcripts, read and replace the stored LLM
provider API key, and change or delete stored meetings.

| Field | Value |
| --- | --- |
| Affected | Meetily through `v0.5.0` (reproduced) and the current `main` line; the public report covers versions through 0.4.1 |
| Fixed | none at disclosure; the vendor calls the client-server architecture deprecated but the vulnerable backend is still present on `main` |
| Severity | CVSS 3.1 7.3 (High) — `AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:L`; CWE-287 / CWE-306 |

The public report is <https://github.com/Zackriya-Solutions/meetily/issues/845>.
The vendor closed it as not planned because the project is moving to a single
Tauri application, not because the code was fixed. The report covers versions
through 0.4.1; tag `v0.5.0` — the newest release — still ships the identical
`backend/app/main.py`, so the exposure extends past the report's scope.

## How does the detector verify the exposure?

1. `GET /openapi.json` must return a JSON OpenAPI document whose `info.title`
   is exactly `Meeting Summarizer API`, whose `info.description` is exactly
   `API for processing and summarizing meeting transcripts`, and whose
   `paths` include the Meetily route set (`/get-meetings`,
   `/get-meeting/{meeting_id}`, `/get-model-config`, `/save-model-config`,
   `/get-transcript-config`, `/save-transcript-config`, `/process-transcript`,
   `/save-transcript`, `/get-summary/{meeting_id}`, `/search-transcripts`,
   `/get-api-key`, `/get-transcript-api-key`, `/save-meeting-title`,
   `/save-meeting-summary`, `/delete-meeting`).
2. `GET /get-meetings` on the same origin must return HTTP 200 with a JSON
   array whose entries (if any) each carry a string `id` and a string `title`.
   The list may be empty on a fresh instance; an empty list still proves the
   business endpoint is reachable anonymously.

The detector reads only route names and the number of meeting entries. It
never requests `/get-api-key`, `/get-transcript-api-key`, `/get-model-config`,
`/get-transcript-config` or a transcript, and it performs no mutation and
sends no credential or cookie. The advisory's API-key disclosure and transcript modification
impact is **not** exercised or claimed.

A deployment that puts the backend behind an authenticating proxy answers 401
on `/openapi.json` and is not reported. A deployment that leaves
`/openapi.json` public but authenticates `/get-meetings` answers 401 on the
business endpoint and is not reported. A different FastAPI app (different
title/description or route set) and a Meetily-shaped app (an app that matches
the `Meeting Summarizer API` title/description and route set but deviates from
the response contract) that returns an object instead of the meeting list are
not reported.

## What does the detector miss?

- A deployment that disables the FastAPI OpenAPI document (`docs_url=None`,
  `openapi_url=None`) fails attribution and is inconclusive.
- Partial protection is a false negative: a deployment that authenticates only
  the probed paths is not reported even though its other routes may still be
  open.
- The detector proves the anonymous meeting-list read. It does not request the
  provider-key or transcript endpoints, so it does not demonstrate that a key
  or transcript was read.
- A reverse proxy that rewrites the backend path or a deployment under a path
  prefix is not probed.
- A meeting list larger than the 256 KiB read bound is inconclusive.
- Network errors, timeouts, truncated or oversized responses and unsupported
  schemes are inconclusive; a missing finding is not proof that the backend is
  protected.

## How to reproduce and remediate

Observe the anonymous OpenAPI document and meeting list yourself:

```sh
curl -sS 'http://<target>:5167/openapi.json' | \
  python3 -c 'import json,sys; d=json.load(sys.stdin); print(d["info"]); print(sorted(d["paths"]))'
curl -sS -i 'http://<target>:5167/get-meetings'
```

A vulnerable backend returns the `Meeting Summarizer API` document with the
Meetily route set and an HTTP 200 JSON meeting list. An authenticating proxy
returns 401.

Remediate the exposure and limit any prior access:

- Bind the backend to `127.0.0.1`, remove the published port from the Docker
  Compose deployment, or put it behind an authenticating reverse proxy.
- Migrate to the unified application.
- Rotate the stored LLM provider API key. Every route was reachable without
  credentials, so assume the key is disclosed.
- Treat all meeting transcripts and summaries as potentially read or modified.
- Review backend access logs for `/get-api-key`, `/get-transcript-api-key`,
  `/get-model-config`, `/get-transcript-config`, `/save-*` and
  `/delete-meeting`.

For the agent-side summary, run `oxo vulnz describe -v CVE-2026-127286`.

## How do I run this detector?

The detector runs automatically during an `oxo` scan of a responding Meetily
backend; no flag is required. To restrict a scan to this CVE:

```sh
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-127286"]' url http://<target>:5167
```

## How was the detector validated against real upstream releases?

**TP 2 / TN 4 / FP 0 / FN 0 / inconclusive 0** (6 real cases): two real upstream
releases were detected, and the two authenticated deployments and two benign
lookalikes were not. A Meetily-shaped app matches the `Meeting Summarizer API`
title/description and route set but deviates from the response contract.

The registered `CVE2026127286Exploit` was exercised from a separate network
client against real upstream tags on loopback, with an independent stdlib
`http.client` oracle that never imports the detector:

| Fixture | Oracle | Detector | Result |
| --- | --- | --- | --- |
| Meetily v0.4.1, seeded synthetic meeting | anonymous meeting list | 1 finding | TP |
| Meetily v0.5.0 (newer release), seeded synthetic meeting | anonymous meeting list | 1 finding | TP (variant) |
| v0.4.1 behind an authenticating reverse proxy | 401 | no finding | TN (fixed deployment) |
| Meetily-shaped app with an authenticated meeting endpoint | 401 on `/get-meetings` | no finding | TN (fixed) |
| unrelated FastAPI app | different OpenAPI | no finding | TN (benign) |
| Meetily-shaped app with a non-list meeting body | wrong list shape | no finding | TN (benign) |

The v0.5.0 variant confirms the backend is unchanged in a newer release; no
upstream fixed release exists, so the two fixed controls are authenticated
deployments of the real backend.

Focused suites: `tests/exploits/meetily_backend_test.py` and
`tests/exploits/cve_2026_127286_test.py` (26 tests), plus the registry and
definitions suites and the real `custom_cve_list` registration test.

## What is not covered by this module?

This module does not claim generic missing-authentication coverage. The
reusable pattern — a management/backend API with no authentication whose
framework metadata and a business read endpoint are anonymously reachable — is
handed off to the general-rule track's open anonymous-management-UI and
credential-bypass/RBAC coverage.
