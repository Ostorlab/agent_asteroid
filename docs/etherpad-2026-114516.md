# CVE-2026-114516: Etherpad pre-authentication static-asset path traversal

**[CVE-2026-114516](https://nvd.nist.gov/vuln/detail/CVE-2026-114516) is an
unauthenticated arbitrary file read** in Etherpad's `/static/*` handler
(CWE-22, CVSS 3.1 9.8). From 1.8.14 through 3.3.2
`src/node/utils/Minify.ts` converted backslashes to forward slashes after
`src/node/utils/sanitizePathname.ts` had already performed its POSIX path
checks. On Linux a backslash is an ordinary filename byte, so an encoded
`..%5C` segment passed the sanitizer and became a real `../` after
`path.join(pluginPath, libraryPath)`. The route is mounted on
`expressPreSession` before the authentication middleware, and the
always-registered `ep_etherpad-lite` pseudo-plugin takes the vulnerable
branch, so any client that can reach the HTTP port reads any file available to
the Etherpad process.

The advisory's high-value targets are `settings.json`, `credentials.json` and
`/proc/self/environ`, which hold the administrator password and session key;
that leads to an admin session and in-process code execution through the
plugin installer.

**Affected:** Etherpad 1.8.14 through 3.3.2 ([GHSA-mc8w-wjhw-45x5](https://github.com/ether/etherpad/security/advisories/GHSA-mc8w-wjhw-45x5))

**Fixed:** Etherpad 3.3.3 ([fix commit 9c8d16d](https://github.com/ether/etherpad/commit/9c8d16d50e2fdfd9693ab35c43280410cb4db2fc)).
The fix performs the backslash conversion only on Windows and adds a backend
regression test.

**Severity:** CVSS 3.1 9.8 (Critical) —
`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`

Every default deployment that exposes the HTTP port is affected. A
pass-through reverse proxy does not mitigate the traversal because `%5C` is
forwarded unchanged; only a proxy that rejects or normalizes encoded
backslashes and dot segments stops the request, which is also why such
deployments are not reported by this detector.

## How does the detector verify the traversal?

1. The product's own non-sensitive `src/package.json` is read one directory
   above the static asset directory through
   `/static/plugins/ep_etherpad-lite/static/..%5Cpackage.json`. The response
   must be a JSON object whose `name` is `ep_etherpad-lite` (or `etherpad`)
   and whose `version` is in `1.8.14 <= version < 3.3.3`. The file the
   vulnerable handler returns is authoritative product attribution, so a
   deployment whose landing page requires authentication can still be
   identified.
2. The same path naming a missing file must answer HTTP 404, so a catch-all
   server that serves any path is not reported.
3. `GET /` is recorded as supplementary evidence when it is reachable: an
   exact `<title>Etherpad</title>` element, or the template's `localizations`
   link to `locales.json` together with the `/manifest.json` link.

The check reads only Etherpad's own non-sensitive `src/package.json` project
metadata. It never requests `settings.json`, `credentials.json`,
`/proc/self/environ`, `/etc/passwd` or any other sensitive file, and it changes
no state.
A fixed 3.3.3 server answers HTTP 404 to the encoded path.

## What does a positive finding claim?

The finding confirms the unauthenticated path traversal: the encoded backslash
segment escaped the static asset directory and the server returned its own
`src/package.json` while the same path naming a missing file returned 404. It
does not claim that `settings.json`, `credentials.json` or any credential was
read; that part of the advisory's impact was deliberately not exercised.

## What does the detector miss?

- A reverse proxy that rejects or normalizes encoded backslashes or dot
  segments prevents the probe from returning `src/package.json` even when the
  backend is vulnerable, so no finding is reported.
- A deployment mounted under a path prefix is not probed; the check uses the
  origin's standard paths.
- A source tree that omits `src/package.json` (some repackaged builds) cannot
  be version-checked, so it is not reported.
- Network errors, timeouts, redirects, oversized bodies and malformed JSON are
  inconclusive and produce no finding; a missing finding is not proof that the
  traversal is absent.

## How do I run the check?

```sh
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-114516"]' ip 10.0.0.10
```

The equivalent manual differential on the same origin is:

```sh
curl -i 'http://10.0.0.10:9001/'
curl -i --path-as-is \
  'http://10.0.0.10:9001/static/plugins/ep_etherpad-lite/static/..%5Cpackage.json'
curl -i --path-as-is \
  'http://10.0.0.10:9001/static/plugins/ep_etherpad-lite/static/..%5Costorlab-missing-package.json'
```

| Request | Vulnerable 3.3.2 / 2.2.0 | Fixed 3.3.3 |
| --- | --- | --- |
| `GET /` | `200` Etherpad landing | `200` Etherpad landing |
| `/static/plugins/ep_etherpad-lite/static/..%5Cpackage.json` | `200` `src/package.json` | `404` |
| `.../..%5Costorlab-missing-package.json` | `404` | `404` |

Run the three commands against the same origin and compare the status codes
with the table above.

## How do I fix CVE-2026-114516?

Upgrade Etherpad to 3.3.3 or later and restart the service. While preparing the
upgrade, restrict the HTTP endpoint to trusted clients and deploy a reverse
proxy that rejects or normalizes encoded backslashes and dot segments in the
request path. Do not rely on Etherpad's authentication settings: the affected
route is mounted before the authentication middleware, so enabling
`requireAuthentication` does not mitigate it.

If an affected deployment was reachable by untrusted clients, treat
`settings.json`, `credentials.json` and the process environment as exposed.
Rotate the administrator password, the session key and any database or SSO
secrets, and review the access log for `/static/` requests containing `%5C`.
