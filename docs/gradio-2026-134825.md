# CVE-2026-134825: Gradio run-history authentication bypass via a forged Host header

**[CVE-2026-134825](https://nvd.nist.gov/vuln/detail/CVE-2026-134825) is an
unauthenticated authentication bypass by spoofing** in Gradio (CWE-290,
CVSS 4.0 8.3, CVSS 3.1 6.5). Gradio 6.27.0 introduced durable run history
backed by Hugging Face buckets. In `gradio/history.py`, `resolve_token()`
returns the caller's OAuth token, or falls back to the token the host saved
with `hf auth login` when `_is_direct_local_request()` considers the request
local. That test requires both a loopback `Host` header and a loopback network
peer.

A Gradio app launched with `ssr_mode` runs a local Node SSR proxy that
connects to the Python app from loopback, and an app behind a reverse proxy on
the same machine has the same shape. Every proxied request therefore passes
the peer half of the check, and the `Host` header alone decides. A remote
client that sends `Host: localhost` inherits the operator's saved Hugging Face
token on the run-history routes, which can then list buckets, read records and
assets, and write buckets under the operator's account.

**Affected:** Gradio 6.27.0 before 6.32.0
([VulnCheck advisory](https://www.vulncheck.com/advisories/gradio-6.27.0-before-6.32.0-authentication-bypass-via-forged-host-header),
[fix commit fda8037](https://github.com/gradio-app/gradio/commit/fda8037b83f316454e96201dfad96e50944f8547))

**Fixed:** Gradio 6.32.0
([fix PR #14050](https://github.com/gradio-app/gradio/pull/14050)), which
removes the host's locally saved token from run-history credential resolution.

**Severity:** CVSS 4.0 8.3 (High) —
`AV:N/AC:H/AT:P/PR:N/UI:N/VC:H/VI:L/VA:N/SC:N/SI:N/SA:N`; CVSS 3.1 6.5

The bypass needs three deployment conditions: a loopback peer (Gradio's SSR
front end or a same-host reverse proxy), a Hugging Face token saved on the host
with `hf auth login`, and an affected Gradio release. An app on a fixed
release, an app with no saved token, an app that disabled run history, or a
proxy that overwrites the inbound `Host` header does not satisfy the
differential.

## How does the detector verify the bypass?

1. `GET /config` must return the Gradio blocks document: a `components` list,
   a `dependencies` list, a `mode` of `blocks`, `interface`, `chat` or
   `custom`, a safe `api_prefix` route prefix, and a stable numeric `version`
   in 6.27.0 through 6.31.x. A lookalike dashboard, a non-200 response, a
   missing prefix or a release outside the interval is not attributed.
2. The ordinary anonymous `GET <api_prefix>/run-history/buckets` is sent with
   the scan target's own `Host` header. The route must answer HTTP 401 with
   Gradio's run-history denial. A 404 (run history disabled), a 200 or any
   other status is not the differential.
3. The same anonymous `GET` is sent once with `Host: localhost`. A vulnerable
   app answers HTTP 200 with the JSON bucket list, or HTTP 502 with Gradio's
   `hub error` when the saved token was accepted but the Hub call failed. A
   fixed 6.32.0 app refuses both requests with HTTP 401.
4. The finding keeps the status codes and the bucket count. The response body
   is inspected for the `buckets` list and then discarded: no bucket name,
   record, asset, token or credential is retained or reported.

Only anonymous GETs are sent. The probe sends no cookie, credential or
write-token header, follows no redirect, and attempts no record/asset read or
bucket write.

## What does a positive finding claim?

The finding confirms the `Host`-header authentication bypass: the run-history
route refused the target's ordinary `Host` and accepted `Host: localhost`
without any credential, so the server resolved the request with the operator's
locally saved Hugging Face token. When the response is HTTP 200 it also
confirms that the token reached the Hub and listed the operator's buckets; when
the response is HTTP 502 `hub error` it confirms token acceptance but not the
bucket list. The finding does not claim that a specific record or asset was
read, or that a bucket was written: those routes were not exercised.

## What does the detector miss?

**Not reported by design (true negatives):** Gradio 6.32.0 and later, a 6.27.0
through 6.31.x app with no saved Hugging Face token, an app with run history
disabled, a proxy that overwrites the `Host` header, and a non-Gradio JSON
document are correctly not reported.

**Coverage gaps (inconclusive):**

- An app exposed directly to a non-loopback client, with no SSR front end and
  no same-host reverse proxy, has a non-loopback peer; the differential cannot
  occur and the app is not reported even if an affected release is installed.
- An app whose `/config` route is protected, customised beyond the Gradio block
  document shape, or stripped by a proxy is not attributed.
- Scanning the app through its own loopback address produces a loopback control
  and no differential; remote scans are the intended path.
- A target behind a proxy that blocks `/config` or the run-history route
  prevents the probe.
- Network errors, timeouts, redirects, oversized bodies and malformed JSON are
  inconclusive and produce no finding; a missing finding is not proof that the
  bypass is absent.

**Evaluation status:** the oracle, the stand-in Hub log and the detector are
independent processes, but this run authored the case matrix. Independent
held-out evaluation is pending; the results are development validation, not a
production false-positive rate or deployed coverage.

## How do I run the check?

```sh
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-134825"]' ip 10.0.0.10
```

The equivalent manual differential on the same origin is:

```sh
curl -s -o- -H 'Host: 10.0.0.10' \
  'http://10.0.0.10/gradio_api/run-history/buckets'
curl -s -o- -H 'Host: localhost' \
  'http://10.0.0.10/gradio_api/run-history/buckets'
```

A vulnerable 6.31.0 app behind an SSR or same-host proxy answers the first
request with `{"detail":"sign in to use run history"}` (HTTP 401) and the second
with the operator's bucket list (HTTP 200). A fixed 6.32.0 app answers both
with HTTP 401.

## How do I fix CVE-2026-134825?

Upgrade Gradio to 6.32.0 or later. The fixed release no longer hands the host's
locally saved token to a request that merely looks local; run history uses the
visitor's own token from the browser's connect dialog or OAuth session.

Until the upgrade is deployed, overwrite the inbound `Host` header with the
app's public hostname at the reverse proxy or SSR front end instead of
forwarding a caller-supplied value, and do not keep an operator token from
`hf auth login` on a host that serves an untrusted network. If an affected app
ran behind a loopback proxy, treat the operator's Hugging Face token as
potentially exposed: rotate it, review the account's buckets for unexpected
reads or writes, and check the web-server logs for requests to
`/gradio_api/run-history/` with `Host: localhost`.

## How was the detector validated?

The fixtures are the real PyPI releases 6.31.0, 6.32.0, 6.27.0 and 6.26.0,
launched on loopback with a synthetic Hugging Face token and a local stand-in
Hub. An independent stdlib `http.client` oracle established ground truth
without importing the detector and the local Hub log recorded every bearer
token use; the registered detector ran from a separate client process. The
6.31.0 loopback-proxy case used a small stdlib reverse proxy in front of a
non-SSR app, and the rewriting-proxy case overwrote `Host` before forwarding.

| Fixture | Oracle | Detector | Result |
| --- | --- | --- | --- |
| Gradio 6.31.0, `ssr_mode=True`, saved token, stand-in Hub | forged Host got the bucket list; Hub log shows one bearer call | 1 finding | TP |
| Gradio 6.31.0, loopback reverse proxy, saved token | forged Host got the bucket list | 1 finding | TP |
| Gradio 6.31.0, saved token, Hub returns an error | forged Host reached the Hub call (`hub error`) | 1 finding (potential) | TP |
| Gradio 6.27.0, `ssr_mode=True`, saved token | forged Host got the bucket list | 1 finding | TP |
| Gradio 6.32.0 fixed, `ssr_mode=True`, saved token | both requests 401 | no finding | TN |
| Gradio 6.31.0, `ssr_mode=True`, no saved token | both requests 401 | no finding | TN |
| Gradio 6.31.0, run history disabled | both routes 404 | no finding | TN |
| Gradio 6.31.0 behind a rewriting proxy | both requests 401 | no finding | TN |
| Gradio 6.26.0, `ssr_mode=True`, saved token | no run-history route (404) | no finding | TN |
| Non-Gradio JSON dashboard with a buckets route | control already returns 200 | no finding | TN |

**TP 4 / TN 6 / FP 0 / FN 0 / inconclusive 0** (10 live cases). These are
curated fixture results, not a production false-positive rate. The fixture
build, oracle, detector client and raw results are under
`artifacts/asteroid/2026-11-23-gradio-history-host-bypass/` in the shared
memory.

## Is Gradio covered by the web fingerprint?

**Yes: Gradio is now fingerprinted.** `Ostorlab/agent_whatweb` PR [#190](https://github.com/Ostorlab/agent_whatweb/pull/190) adds
`plugins/gradio.rb`, which matches the landing document's `<gradio-app>`
element together with the embedded Gradio configuration. WhatWeb 0.6.4 at
default aggression identified the real 6.31.0, 6.32.0, 6.27.0 and 6.26.0
fixtures as Gradio and did not match a plain HTML page, a JSON-only response or
an unrelated dashboard. Version extraction is a recorded gap: the landing
document carries no release, and WhatWeb does not fetch `/config` at default
aggression. The CVE detector reads the release from `/config` itself.
