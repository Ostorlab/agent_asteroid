# CVE-2026-55508: Wavelog unauthenticated SQL injection in the OQRS callsign search

**[CVE-2026-55508](https://nvd.nist.gov/vuln/detail/CVE-2026-55508) is an
unauthenticated SQL injection** in Wavelog through 2.4.2 (CWE-89, CVSS 3.1 9.4
`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:L`).
`Oqrs_model::search_log()` concatenated the caller-supplied `callsign` POST
value into a raw `WHERE` fragment (`COL_CALL like "%<callsign>%"`), and the
`POST /oqrs/search_log` controller action performed no authorization check.

The handler rendered every matching QSO row in the `oqrs/qsolist` view, so an
unauthenticated attacker could inject SQL and read application database
records. The advisory lists account data, bcrypt password hashes, per-user API
keys, station credentials, password reset tokens and all QSO data, and chains
the reset-token disclosure with the forgot-password workflow for full account
takeover, including administrators.

**Affected:** Wavelog through 2.4.2
([GHSA-rrrq-ch2q-pqmp](https://github.com/wavelog/wavelog/security/advisories/GHSA-rrrq-ch2q-pqmp))

**Fixed:** Wavelog 2.5
([fix commit b65ecbf](https://github.com/wavelog/wavelog/commit/b65ecbfad21f4c14a4ae225b9f804c756701698c),
[release 2.5](https://github.com/wavelog/wavelog/releases/tag/2.5)). The fix
adds an authentication check to the controller and replaces the string
concatenation with bound query parameters.

**Severity:** CVSS 3.1 9.4 (Critical) —
`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:L`

## How does the detector verify the injection?

1. `GET /index.php/user/login` (or `/user/login` when URL rewriting is
   enabled) must return the Wavelog login document. The detector requires both
   the `- Wavelog` title suffix and a Wavelog-specific footer marker, so a
   title-only page or another product is not attributed.
2. `POST /index.php/oqrs/search_log` with a random, callsign-shaped value must
   return HTTP 200 with the empty-search response (`No QSOs were found`). A
   random callsign must not return rows.
3. The same endpoint is called once more with
   `%" OR 1=1 OR COL_CALL like "%`. The value closes the double-quoted `LIKE`
   literal, adds an always-true predicate and reopens the literal so the
   trailing quote in the original query stays balanced.

A vulnerable server returns HTTP 200 with the `oqrs/qsolist` table and at least
one QSO row. A fixed 2.5 server requires authentication and answers HTTP 303
to `/dashboard` for both requests, so the differential cannot be observed.

The probe reads only whether the QSO table rendered and the numeric row ids. It
does not request or retain an account record, password hash, API key, reset
token, station credential or QSO field, and it sends no credential or
mutation. The finding confirms the injection surface; it does not claim that a
specific account, hash or reset token was extracted.

## What does a positive finding claim?

**The finding confirms the unauthenticated SQL injection:** a random callsign
returned the empty-search response, while the injected callsign returned QSO
rows that the baseline did not. That difference proves the callsign value is
concatenated into the SQL executed by `Oqrs_model::search_log()`.

The finding does not claim that the advisory's database read, reset-token
disclosure or account takeover was performed. Those are the documented
consequences of the confirmed injection and were not exercised.

## What does the detector miss?

**The detector does not report a deployment when it cannot observe the
differential.** The enumerated cases are:

- A Wavelog instance with no QSO rows returns the empty-search response for the
  injected predicate as well, so the injection is not demonstrated. A fresh or
  unused logbook is therefore inconclusive, not clean.
- A fixed 2.5 or later deployment redirects the unauthenticated request and is
  not reported.
- A reverse proxy or WAF that blocks `/oqrs/search_log`, or a deployment that
  restricts the OQRS routes to authenticated users, prevents the probe.
- A customized login page without both the `- Wavelog` title suffix and the
  Wavelog footer is not attributed; a login mounted at a non-standard route is
  not probed.
- A catch-all that returns rows for every callsign fails the empty-baseline
  requirement and is not reported.
- Network errors, timeouts, redirects, oversized bodies and non-HTML responses
  are inconclusive and produce no finding; a missing finding is not proof that
  the injection is absent.

## How do I run the check?

```sh
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-55508"]' ip 10.0.0.10
```

Wavelog listens on port 80 or 443 behind its web server by default; adjust the
port in each command if the deployment differs. The equivalent manual
differential on the same origin is:

```sh
# Attribution: the login page carries the Wavelog title and footer.
curl -i 'http://10.0.0.10/index.php/user/login'

# Baseline: a random callsign returns the empty-search response.
curl -i -X POST 'http://10.0.0.10/index.php/oqrs/search_log' \
  --data-urlencode 'callsign=ORACLEPROBE123456'

# Injection: the always-true predicate returns QSO rows.
curl -i -X POST 'http://10.0.0.10/index.php/oqrs/search_log' \
  --data-urlencode 'callsign=%" OR 1=1 OR COL_CALL like "%'
```

| Request | Vulnerable 2.4.2 | Fixed 2.5 |
| --- | --- | --- |
| `GET /index.php/user/login` | `200 Login - Wavelog` | `200 Login - Wavelog` |
| search, random callsign | `200`, `No QSOs were found` | `303` to `/dashboard` |
| search, injected callsign | `200`, `qsolist` table with rows | `303` to `/dashboard` |

A deployment that answers the injected request with the same empty-search
response may be fixed, may have no QSO rows, or may be fronted by a filter;
treat that result as inconclusive rather than clean.

## How do I fix CVE-2026-55508?

1. Upgrade Wavelog to 2.5 or later, which adds the controller authorization
   check and binds the callsign parameter, then restart the service.
2. If upgrading is not immediately possible, block external access to
   `/oqrs/search_log` at the reverse proxy or web server, and restrict the
   OQRS routes to authenticated users.
3. If an earlier build was reachable by untrusted clients, review access logs
   for `/oqrs/search_log` requests containing quote characters, `OR`/`UNION`
   keywords or comment markers while the deployment was exposed.
4. Treat database contents reachable by the Wavelog database account as
   potentially disclosed: rotate the database credential and the per-user API
   keys and station credentials, and invalidate outstanding password reset
   tokens.
5. Review administrator accounts and recent account changes for activity you
   cannot explain, since the advisory chains reset-token disclosure with the
   forgot-password flow for account takeover.

## Companion WhatWeb fingerprint

The companion rule lives in `Ostorlab/agent_whatweb` as
`plugins/wavelog.rb` (agent_whatweb 2.0.15). WhatWeb follows the landing
redirect to the login document and matches the `- Wavelog` title suffix
together with the Wavelog footer phrase, so the title-only and footer-only
lookalikes are not fingerprinted. The release is not present in the login
response, so version extraction is a recorded gap for the inventory.
