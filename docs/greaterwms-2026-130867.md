# GreaterWMS CVE-2026-130867 unauthenticated path traversal

**CVE-2026-130867** is an unauthenticated path traversal in GreaterWMS through
2.1.54, an open-source warehouse management system. The `css`, `js`,
`statics` and `fonts` routes build a filesystem path by concatenating the
decoded `request.path_info` onto `BASE_DIR/templates/dist/spa` and open it
without normalization or containment (CWE-22; CVSS 3.1 7.5
`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`, CVSS 4.0 8.7).

An encoded `../` sequence therefore escapes the asset directory and reads any
file the backend process can read. In the shipped Docker deployment the
repository is bind-mounted at `/GreaterWMS`, so `db.sqlite3` is reachable; its
`openid` values are accepted by `utils/auth.py` as permanent bearer
credentials, which turns the read into account takeover.

The upstream issue
[GreaterWMS#415](https://github.com/GreaterWMS/GreaterWMS/issues/415) documents
the flaw and a proof of concept; it was closed on 2026-11-17 without a code
change. No fixed release is published: `master` and the `new` branch still
concatenate the raw path.

## Which advisory and references confirm the vulnerability?

- NVD: <https://nvd.nist.gov/vuln/detail/CVE-2026-130867> (published
  2026-11-18T21:17Z, CWE-22, CVSS 3.1 7.5 / CVSS 4.0 8.7).
- CVE record: <https://www.cve.org/CVERecord?id=CVE-2026-130867>.
- Upstream issue: <https://github.com/GreaterWMS/GreaterWMS/issues/415>.
- Vulnerable tree:
  <https://github.com/GreaterWMS/GreaterWMS/blob/V2.1.54/greaterwms/views.py>.
- URL patterns:
  <https://github.com/GreaterWMS/GreaterWMS/blob/V2.1.54/greaterwms/urls.py>.

`views.css()` is the representative shape:

```text
def css(request):
    path = str(settings.BASE_DIR) + '/templates/dist/spa' + request.path_info
    content_type, encoding = mimetypes.guess_type(path)
    resp = StreamingHttpResponse(FileWrapper(open(path, 'rb')), content_type=content_type)
    resp['Cache-Control'] = "max-age=864000000000"
    return resp
```

`js`, `statics` and `fonts` are identical. `settings.BASE_DIR` is the
repository root and `db.sqlite3` lives there by default.

## How does the detector verify the traversal?

1. Read `GET /` and require the exact landing title
   `GreaterWMS--Open Source Warehouse Management System`.
2. Read `GET /api/` with `Accept: application/vnd.oai.openapi` and require the
   public OpenAPI document to carry `openapi:` and `info.title: GreaterWMS`.
   This route is anonymous in the affected tree and does not depend on the
   vulnerable handler.
3. Read the packaged `GET /statics/icons/logo.png` control and require HTTP
   200 with the PNG signature, proving the static handler serves its intended
   directory.
4. Send `GET /css/..%2f..%2f..%2f..%2fmanage.py` and require HTTP 200,
   a non-HTML content type, and the project markers
   `DJANGO_SETTINGS_MODULE` plus `greaterwms.settings`. If `manage.py` is not
   present, send
   `GET /css/..%2f..%2f..%2f..%2fgreaterwms%2fsettings.py` and require
   `ROOT_URLCONF = 'greaterwms.urls'` plus `DATABASES = {`.

Only the project's own non-sensitive source file and the packaged logo are
read. The detector never requests `db.sqlite3`, a user row, an `openid` token,
a credential or any other file. It sends no credential, cookie or body,
follows no redirect and changes no state.

## What does a positive finding claim?

The finding confirms that an anonymous request read a GreaterWMS project
source file through the static route, outside the intended asset directory. It
does **not** claim that the database, a user account or an `openid` token was
read, and it does not assert that the deployment is exactly 2.1.54: custom
routing or a different asset layout can expose the same handler elsewhere.

A deployment that confines the resolved path to the asset root, a route that
answers 400/403/404, and a lookalike that lacks the project source markers are
not reported.

## What does the detector miss?

- A reverse proxy that decodes and normalizes dot segments before forwarding
  defeats the probe, so the traversal is not observed.
- A deployment that removes `manage.py` and `greaterwms/settings.py`, or
  serves the backend from a packaged wheel without the repository tree, is not
  confirmed even if other files remain readable.
- A custom landing page that removes the title, or a removed `/api/` document,
  is not attributed.
- The version is not observable from the landing document; `/api/` carries a
  stale `2.1.48`. The check is behavioural and does not depend on a version.
- Network errors, timeouts, redirects and oversized attribution documents are
  inconclusive; the absence of a finding is not proof that the target is
  patched.

## How do I remediate?

There is no fixed upstream release. Contain every static-asset path before
opening it: resolve the candidate with `os.path.realpath` or
`pathlib.Path.resolve` and reject it unless it is inside
`templates/dist/spa`, and reject any decoded segment that is `..`. Until an
upstream fix ships, also block encoded dot segments at the reverse proxy, move
`db.sqlite3` outside the web process's readable tree, and point
`DATABASES['default']['NAME']` (or the equivalent environment setting) at the
new location so the application still starts.

Treat every `openid` value as disclosed: invalidate the stored tokens, force
re-authentication for all accounts, and review the users table for unexpected
staff or administrator accounts.

## How do I run this detector?

The detector runs automatically during an `oxo` scan of a reachable GreaterWMS
deployment. To restrict a scan to this CVE:

```sh
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-130867"]' url http://<greaterwms-host>:8008
```

The official compose publishes the daphne backend on port `8008` and the
Quasar frontend on port `8080`; the API and the vulnerable routes are on the
backend.

## How was the detector validated?

The real `V2.1.54` tree
(`8344f3872155d75acce5c5d5d7d95b5b8e18dfc1`) was served through Django's
development WSGI server and through the shipped `daphne`
`greaterwms.asgi:application` entrypoint; the real `V2.1.52` tree
(`f1ee450c49fe2f86cbab245317c645280c198fe9`) was served through `daphne` as the
second vulnerable release. A third V2.1.54 copy carried a containment patch
(resolve the path, reject anything outside `templates/dist/spa`) as the fixed
control. Six stdlib lookalikes exercised a removed landing title, a
GreaterWMS-shaped OpenAPI whose decoy 200 body lacked the project markers, a
missing logo, a catch-all HTML response, a foreign product whose traversal
returned project-shaped source, and a 302 to the login page. An independent
stdlib `http.client` oracle fetched the landing page, the OpenAPI document, the
logo, the traversal response, and the SQLite database header; the registered
`CVE2026130867Exploit` ran from a separate client process.

| Fixture | Oracle | Detector | Result |
| --- | --- | --- | --- |
| V2.1.54 under daphne, `manage.py` reachable | traversal + SQLite header read | finding | TP |
| V2.1.52 under daphne | traversal + SQLite header read | finding | TP |
| V2.1.54 under Django dev server | traversal + SQLite header read | finding | TP |
| V2.1.54 with containment patch | traversal 404, logo 200 | no finding | TN |
| Landing title only, no GreaterWMS OpenAPI | not attributed | no finding | TN |
| GreaterWMS-shaped OpenAPI, decoy 200 source body | markers absent | no finding | TN |
| GreaterWMS-shaped landing/API, logo missing | control failed | no finding | TN |
| SPA catch-all answers 200 HTML for the traversal | not a project source | no finding | TN |
| Foreign product, traversal returns project-shaped source | not attributed | no finding | TN |
| GreaterWMS-shaped product, traversal 302 to login | redirect not followed | no finding | TN |

**TP 3 / TN 7 / FP 0 / FN 0 / inconclusive 0.**

The traversal response on the three vulnerable fixtures was
`HTTP 200 text/x-python` beginning `#!/usr/bin/env python` and containing
`os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'greaterwms.settings')`; the
fixed fixture answered `HTTP 404 text/html` for both `manage.py` and
`settings.py` while still serving the logo. The oracle, not the detector,
read the SQLite header.

## What does the optional inventory assessment add?

The same module also keeps an owner-evidence assessor. It runs locally through
`python -m agent.utils.inventory` and makes no network requests, so its result
is only as strong as the inspection it records. Save one record per deployment
in a JSON array:

```json
[
  {"product": "GreaterWMS", "static_route_enabled": true, "static_root_containment_verified": false},
  {"product": "GreaterWMS", "static_route_enabled": false},
  {"product": "GreaterWMS", "static_route_enabled": true, "static_root_containment_verified": true},
  {"product": "GreaterWMS", "static_route_enabled": true, "static_root_containment_verified": true, "conflicting_evidence": true}
]
```

Run `python -m agent.utils.inventory inventory.json`.

- **`potential_exposure`** means the operator found an enabled route with no
  containment check, as in the first record.
- **`not_matched`** means the operator verified that the route is disabled or
  that the enabled route enforces containment.
- **`inconclusive`** means the record lacks evidence needed for a decision or
  declares conflicting evidence.

Omit fields whose values you could not establish. Set
`conflicting_evidence` to `true` when sources disagree. The remote detector,
not this assessor, is what establishes live exposure during a scan.
