# Flagr CVE-2026-130860 default basic-auth whitelist bypass

**CVE-2026-130860 is an authentication bypass** in Flagr before 1.2.5. The
documented basic-auth setup leaves `FLAGR_BASIC_AUTH_WHITELIST_PATHS` at
`/api/v1/health,/api/v1/flags,/api/v1/evaluation,/api/v1/exposures`.
`basicAuth.whitelist()` in `pkg/config/middleware.go` matches each entry as a
path prefix without looking at the HTTP method, so `/api/v1/flags` also admits
every nested flag-management write: create and update a flag, enable or
disable it, delete it, and create or update its variants, segments,
constraints and distributions.

**Affected:** Flagr before 1.2.5 (VulnCheck: `>= 0, < 1.2.5`)
**Fixed:** 1.2.5 (commit `c7e995e`, PR #814)
**Severity:** CVSS 3.1 8.2 (High) — `AV:N/AC:L/PR:N/UI:N/C:N/I:H/A:L`; CWE-1188

The default whitelist existed at least as far back as the 1.1.x line. It is an
insecure default, not a code-path bug in each handler: the CRUD handlers add
no authentication of their own. The precondition is that the operator enabled
basic auth (`FLAGR_BASIC_AUTH_ENABLED=true`); with authentication off, all of
Flagr is already open and this CVE's specific failure (an auth bypass) is not
present.

## How does the detector verify the bypass?

1. `GET /api/v1/health` must return exactly `{"status":"OK"}`, Flagr's health
   document.
2. `GET /api/v1/tags` must return HTTP 401 with Flagr's own
   `WWW-Authenticate: Basic realm="you shall not pass"` challenge and the
   plain `Not authorized` body. `/api/v1/tags` is not in the default
   whitelist, so this proves that basic auth is enabled and enforced on a
   non-whitelisted management route. A different realm, a 200, or a different
   body stops here.
3. `GET /api/v1/flags` must return a JSON array, the anonymous flag list.
4. `POST /api/v1/flags` sends the intentionally incomplete body `{}`. A
   vulnerable deployment passes the request through the whitelist to the CRUD
   validation layer, which answers
   `422 {"code":602,"message":"description in body is required"}`. A fixed
   1.2.5 deployment, or one whose whitelist excludes `/api/v1/flags`, answers
   401 before the handler; `evalOnlyMode` answers 403.

The empty body fails the required `description` check during request binding,
so the create handler never runs: no flag, variant, segment, constraint or
distribution is created, changed or deleted. The probe sends no credential,
cookie, session or valid write payload.

## What does a positive finding claim?

The finding confirms that, on a Flagr deployment where basic auth is active,
the flag-management write route is reachable without authentication and passes
an anonymous request to the CRUD layer. That is the CVE-2026-130860
misconfiguration. The finding does **not** claim that a flag was created or
modified, and it does not exercise the advisory's create/enable/delete steps.

## What does the detector miss?

- The Flagr release is not exposed by the unauthenticated landing response.
  Once basic auth is enabled, `/swagger.json` and the UI document are both
  challenged, so the detector cannot distinguish the vendor default in a
  release before 1.2.5 from an explicit custom whitelist that re-adds
  `/api/v1/flags` on any later release. Both expose the write API the same
  way; the finding cannot attribute the open write route to a specific Flagr
  release and does not claim the deployment is pre-1.2.5.
- A deployment that only enables JWT auth gets a different challenge and is
  not probed. The vendor default JWT whitelist does not contain
  `/api/v1/flags`, so that population is not this CVE.
- A custom whitelist that also covers `/api/v1/tags` cannot be used to prove
  that basic auth is enforced, so such a deployment is not reported even when
  the flags route is open.
- A reverse proxy that answers the `/api/v1/tags` challenge with its own body
  or realm is not attributed. A proxy that blocks the write route is not
  reported.
- A deployment mounted under `FLAGR_WEB_PREFIX` is not probed, because the
  standard paths are not rewritten.
- Network errors, timeouts, redirects, oversized bodies and malformed JSON are
  inconclusive; a missing finding is not proof that the deployment is patched.

## How do I reproduce the bypass safely?

The first three requests are reads. The fourth is a write request with an
invalid body; it does not create anything. Replace the host with the Flagr
base URL.

```sh
curl -sS 'http://<target>/api/v1/health'
# {"status":"OK"}

curl -si 'http://<target>/api/v1/tags'
# HTTP/1.1 401 Unauthorized
# WWW-Authenticate: Basic realm="you shall not pass"
# Not authorized

curl -sS 'http://<target>/api/v1/flags'
# []

curl -si -X POST 'http://<target>/api/v1/flags' \
  -H 'Content-Type: application/json' --data '{}'
# vulnerable: HTTP/1.1 422 Unprocessable Entity
# {"code":602,"message":"description in body is required"}
# fixed:      HTTP/1.1 401 Unauthorized  (basic-auth challenge)
```

## How do I remediate CVE-2026-130860?

1. Upgrade Flagr to 1.2.5 or later and restart it so the new default whitelist
   takes effect.
2. If the whitelist was customised, remove `/api/v1/flags` from the prefix
   list and use `FLAGR_BASIC_AUTH_EXACT_WHITELIST_PATHS` for any public read
   route. A prefix entry admits every method underneath it.
3. Review flag configuration and flag snapshots for unexpected creations,
   edits, enable/disable changes and deletions while the deployment was
   exposed, and restrict network access to the management API.
4. Enabling basic auth alone does not protect the flags route on an older
   release; the whitelist is part of the fix.

## How do I run this detector?

The detector runs automatically during an `oxo` scan of a responding Flagr
instance; no flag is required. To restrict a scan to this CVE:

```sh
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-130860"]' url http://<target>
```

To read the agent-side summary, run
`oxo vulnz describe -v CVE-2026-130860`.

## How was the detector validated?

The registered `CVE2026130860Exploit` was exercised from a separate network
client against the real upstream `1.2.3`, `1.2.4` and `1.2.5` Go binaries on
loopback, built from the pinned tags with Go 1.27.4. An independent stdlib
`http.client` oracle that never imports the detector produced the ground
truth; a non-Flagr lookalike covered the attribution boundary.

| Fixture | Oracle (independent) | Detector | Result |
| --- | --- | --- | --- |
| Flagr 1.2.4, basic auth on, default whitelist | write route reached (422) | 1 finding | TP |
| Flagr 1.2.3, basic auth on, default whitelist | write route reached (422) | 1 finding | TP |
| Flagr 1.2.5, basic auth on, fixed default | `/api/v1/flags` 401 | no finding | TN |
| Flagr 1.2.4, basic auth off | no challenge | no finding | TN |
| Flagr 1.2.4, custom whitelist without `/api/v1/flags` | `/api/v1/flags` 401 | no finding | TN |
| Flagr 1.2.5, explicit custom whitelist that re-adds `/api/v1/flags` | write route reached (422) | 1 finding | TP (same exposure, outside the default range) |
| Non-Flagr lookalike with `{"status":"OK"}`, a 401 and 422 but realm `Restricted` | behavior present, attribution absent | no finding | TN |
| Non-Flagr lookalike with Flagr's realm but health `{"status": "ok"}` | behavior present, attribution absent | no finding | TN |

**TP 3 / TN 5 / FP 0 / FN 0 / inconclusive 0** on the real-fixture matrix.
Focused mocked tests cover the fixed 401, the custom-whitelist 401, the
`evalOnlyMode` 403, an unexpected 200/400/404/500, a different validation
message or code, a different realm, a different challenge body, a non-JSON
health document, a non-array flag list, malformed JSON, an oversized body, a
redirect, an unsupported scheme and a direct `check()` on each lookalike.
Curated fixture results are not a production false-positive rate.

The detector uses only anonymous HTTP requests to the target's own routes, in
the order above, with a 10 s per-request timeout and a 64 KiB response cap.

## Fingerprint

The companion fingerprint is a WhatWeb plugin in `Ostorlab/agent_whatweb`,
`plugins/flagr.rb`, validated with WhatWeb 0.6.4. Both the vulnerable 1.2.4 UI
document and the fixed 1.2.5 basic-auth challenge are identified as **Flagr**;
a page titled `Some Other App` is not. The release version is not present in
either landing response, so the plugin extracts no version and component
matching cannot resolve the patch level from it; that is recorded as a gap.

## Generic handoff (not closed by this module)

The reusable pattern — an authorization middleware that matches a path prefix
without considering the HTTP method, so a read whitelist also admits the
write surface — is recorded as a handoff to the General Rule Creator. This CVE
module does not claim generic method-aware authorization coverage. It also
joins the open trusted-header, URL path-normalization/alternate-route and
management-API route-registration handoffs.
