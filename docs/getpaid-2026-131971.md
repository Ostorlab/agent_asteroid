# CVE-2026-131971: GetPaid unauthenticated invoice disclosure

**[CVE-2026-131971](https://nvd.nist.gov/vuln/detail/CVE-2026-131971) is an
unauthenticated invoice disclosure** in GetPaid (the Invoicing System
WordPress plugin) (CWE-639 Authorization Bypass Through User-Controlled Key,
CVSS 3.1 5.3). In releases 2.6.2 through 2.8.62,
the single-invoice widget `[getpaid_invoice id=<id>]` in
`widgets/invoice.php` loaded the invoice and rendered it without checking
whether the visitor may view it. The public payment-form embed endpoint
`/?getpaid_embed=1&invoice=<id>` runs that widget for an anonymous client, so a
visitor who knows or guesses an invoice id reads the customer's name, billing
address, phone number, line items and payment status.

**Affected:** GetPaid 2.6.2 through 2.8.62
([WPScan 4b26e62a](https://wpscan.com/vulnerability/4b26e62a-29da-4b56-818e-aed7f439831e/))

**Fixed:** GetPaid 2.8.63
([fix source](https://plugins.svn.wordpress.org/invoicing/tags/2.8.63/widgets/invoice.php))

**Severity:** CVSS 3.1 5.3 (Medium) —
`AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N`

An invoice is a publicly queryable WordPress post: with the default GetPaid
permalink structure its slug is `invoice-<post id>`, which is why the WordPress
invoice sitemap publishes the id an anonymous visitor needs for the embed
request. A finding records one rendered invoice: only the invoice id and the
structural markers are kept, and none of the customer data the page renders is
retained.

## How does the detector verify the disclosure?

1. `GET /wp-json/wp/v2/types` must return the WordPress `post` and `page` types
   with their canonical `posts` and `pages` REST bases.
2. `GET /wp-content/plugins/invoicing/readme.txt` must return one of the exact
   GetPaid headings and a single `Stable tag` in 2.6.2 through 2.8.62. A
   missing readme, a different heading or a release outside the interval is not
   attributed. A random missing file under the plugin directory must answer
   404/410, so a catch-all page is not credited.
3. The WordPress invoice sitemap is read from `/wp-sitemap.xml` and the
   `wp-sitemap-posts-wpi_invoice` child sitemap. With the default GetPaid
   permalink structure the public URL is `invoice/invoice-<post id>`, so the id is
   read from the slug; at most five ids are kept. If the sitemap is
   unavailable, a bounded probe of ids 1 through 16 is used instead.
4. `GET /?getpaid_embed=1&invoice=<id>` must answer HTTP 200 with the embed
   wrapper, the `getpaid-invoice-meta-data` container and the invoice-number
   row, and without the fixed release's explicit "You are not allowed to view
   this invoice" denial or "Invoice not found".

Only anonymous GETs are sent. The response body is inspected for those
structural markers and then discarded. No customer name, address, phone
number, line item, payment status or other invoice content is retained,
returned or reported. No credential, cookie or request body is sent, redirects
are not followed, and no state is changed.

## What does a positive finding claim?

The finding confirms that the public embed endpoint rendered an existing
invoice to an unauthenticated client. It records the invoice id and the
markers only. It does not claim that a specific customer record was read by
the scanner, because the detector discards the rendered content.

## What does the detector miss?

**Not reported by design (true negatives):** GetPaid 2.8.63 and later answer
the permission denial; a site with the plugin installed but not activated has
no invoice post type or embed handler; a site with no invoice has nothing to
render; and a non-WordPress copy of the readme does not satisfy the REST types
control.

**Coverage gaps (inconclusive):**

- A site whose invoice permalinks do not end in the post id (a customized
  `post_name`) and whose sitemap is readable is not probed further.
- A site that disables both the WordPress sitemap and the renderable low ids
  (for example, invoices created after many other posts) is a coverage
  limitation, not a clean negative.
- A security plugin that disables `/wp-json/wp/v2/types` or strips the plugin
  readme prevents attribution.
- A reverse proxy that blocks `getpaid_embed` or the invoice query prevents
  the probe. Network errors, timeouts, redirects, oversized bodies and
  malformed XML/JSON are inconclusive and produce no finding; a missing finding
  is not proof that the disclosure is absent.

## How do I run the check?

```sh
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-131971"]' ip 10.0.0.10
```

The equivalent manual differential on the same origin is:

```sh
curl -i 'http://10.0.0.10/wp-json/wp/v2/types'
curl -i 'http://10.0.0.10/wp-content/plugins/invoicing/readme.txt'
curl -i 'http://10.0.0.10/wp-sitemap.xml'
curl -i 'http://10.0.0.10/wp-sitemap-posts-wpi_invoice-1.xml'
curl -i 'http://10.0.0.10/?getpaid_embed=1&invoice=11'
```

A vulnerable 2.8.62 site returns the readme with `Stable tag: 2.8.62`, a
sitemap entry such as `/invoice/invoice-11/`, and a rendered invoice at the
embed URL. A fixed 2.8.63 site answers "You are not allowed to view this
invoice" for the same id.

## How do I fix CVE-2026-131971?

Upgrade the Invoicing System (GetPaid) plugin to 2.8.63 or later, which checks
`wpinv_user_can_view_invoice()` before the single-invoice widget renders. If
the plugin cannot be updated, block anonymous requests to the payment-form
embed endpoint that carry an `invoice` parameter, or restrict that endpoint at
the reverse proxy. Removing invoice URLs from the WordPress sitemap only
reduces casual discovery: ids are sequential and remain enumerable, so treat
it as defense-in-depth, not a fix. Treat invoice ids and their contents as
enumerable: review access logs for
anonymous `?getpaid_embed=1&invoice=` requests, rotate any exposed invoice
keys (GetPaid's per-invoice secret used in payment/access URLs), and notify
customers whose billing details may have been disclosed.

## How was the detector validated?

The fixtures are real GetPaid 2.8.62, 2.8.61 and 2.8.63 release zips running
in WordPress Playground (WordPress 7.1.5, PHP 8.3, SQLite). A blueprint
activated the plugin and created one invoice. An independent stdlib
`http.client` oracle established ground truth without importing the detector,
and the registered detector ran from a separate client process.

| Fixture | Oracle | Detector | Result |
| --- | --- | --- | --- |
| GetPaid 2.8.62, one invoice, public sitemap | vulnerable | 1 finding | TP |
| GetPaid 2.8.61, one invoice, public sitemap | vulnerable | 1 finding | TP |
| GetPaid 2.8.63 fixed, one invoice | fixed | no finding | TN |
| GetPaid 2.8.62, plugin active, no invoice | not vulnerable | no finding | TN |
| GetPaid 2.8.62, plugin installed but inactive | not vulnerable | no finding | TN |
| Plain WordPress without GetPaid | not GetPaid | no finding | TN |
| GetPaid 2.8.62 with the sitemap disabled, invoice at id 11 | vulnerable | 1 finding | TP (fallback) |

**TP 3 / TN 4 / FP 0 / FN 0 / inconclusive 0** (7 live cases). The detector
suite covers the sitemap order, the fallback ids, the fixed denial, a
not-found invoice, a lookalike body, the older readme heading and a
subdirectory install with synthetic responses. These are curated fixture
results, not a production precision or recall rate.

## Is GetPaid covered by the WordPress plugin fingerprint?

**Yes: GetPaid is already fingerprinted.** GetPaid's WordPress.org slug is
`invoicing`, which `agent_wordpress` lists in
`agent/analyzers/files/plugin_slugs.txt`. Its plugin enumeration identifies the
plugin and extracts the readme release without a new fingerprint PR; the live
2.8.61, 2.8.62 and 2.8.63 fixtures were all reported as
`invoicing` with the matching version.
