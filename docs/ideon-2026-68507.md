# CVE-2026-68507: ideon unauthenticated link-preview SSRF

**CVE-2026-68507** is a server-side request forgery in
[ideon](https://github.com/3xpyth0n/ideon), a self-hosted Next.js visual
workspace. Before 0.9.5 the `POST /api/links/preview` handler passed a
caller-supplied URL to `fetchLinkMetadata` and returned the scraped title,
description and image. The route had no session check of its own; the Next.js
`proxy.ts` middleware normally answered `401` for unauthenticated API requests,
but it depends on NextAuth and fails open when its secret is missing (NextAuth
`MissingSecret`), so the request continued to the route.

The `isPrivateIP` blocklist rejected `127.0.0.1`, `localhost`, `::1`, RFC1918
and link-local literals but not the unspecified address. On Linux
`http://0.0.0.0:<port>/<path>` is routed to `127.0.0.1`, so the route reached
the server's own listener (CWE-306/CWE-918, CVSS 4.0 6.9
`AV:N/AC:L/AT:N/PR:N/UI:N/VC:N/VI:L/VA:N`).

An unauthenticated caller therefore reached a route the proxy was supposed to
gate, and could read the scraped title, description or image of any HTML
service bound to the host's loopback; the preview endpoint acted as an
anonymous loopback relay until 0.9.5 added the route-level `getAuthUser()`
check.

Version 0.9.5 adds a `getAuthUser()` check to the route (`401` before reading
the URL) and rejects `0.0.0.0`, `::` and `0.0.0.0/8` in the blocklist. 0.9.6
closed the wider IPv4-mapped, NAT64, 6to4 and Teredo gap for authenticated
users ([CVE-2026-103980](https://nvd.nist.gov/vuln/detail/CVE-2026-103980)).

Checked 12 November 2026 against v0.9.3, v0.9.4 and v0.9.5.

The advisory's description says the project has no middleware. That is
imprecise: `src/proxy.ts` exists and gates API routes when NextAuth has a
secret. The route-level check added in 0.9.5 is what removes the dependency on
the proxy's secret and configuration.

## How does the detector verify the SSRF?

1. Read `/site.webmanifest` and require the `name` (and, when present,
   `short_name`) to be `IDEON`. Read `/api/system/current-version` when the
   proxy allows it and parse the release.
2. Find a public HTML page: `/setup` (first-run wizard) or `/login`
   (installed instance), requiring a `<title>` that contains `Ideon`.
3. If the observed release is 0.9.5 or later, stop: the route-level guard and
   the blocklist fix are present. If the release cannot be read because the
   proxy blocks `/api/system/current-version`, skip this stop and continue to
   the behavioural probes in steps 4-5.
4. Otherwise `POST /api/links/preview` with
   `{"url":"http://0.0.0.0:<observed-port><page>"}` and require HTTP 200 plus
   a returned `title` equal to the page title read directly from the origin.
   That proves the server fetched its own page for a request with no session
   cookie and that the `0.0.0.0` spelling bypassed the loopback guard.
5. Send the same POST with `http://127.0.0.1:<observed-port><page>` and
   require an empty title, so the guard is shown to be present and `0.0.0.0`
   is the bypass rather than an absent blocklist.

Only the origin's own page is requested. The detector never asks the server to
contact a third-party host, an internal service, a cloud-metadata endpoint or
application data, and it changes no state.

## How was the detector validated?

Real upstream releases were built with Node.js 22 and `next build --webpack`.
Each instance ran on loopback with its own SQLite `storage/` directory. v0.9.4
and v0.9.3 were started **without** `SECRET_KEY`, which is the fail-open proxy
condition; a second v0.9.4 instance was started **with** `SECRET_KEY` to cover
the proxy-enforced deployment. v0.9.5 was started without `SECRET_KEY` to show
the route-level guard still refuses the request.

An independent stdlib oracle read each fixture's `package.json` and
`src/app/api/links/preview/route.ts`, then exercised the public manifest,
release, setup page and preview endpoint with raw HTTP; it never imported the
detector. Two stdlib lookalikes cover a different manifest name and a missing
preview route.

| Case | Kind | Oracle | Detector |
| --- | --- | --- | --- |
| v0.9.4, no `SECRET_KEY` | vulnerable | vulnerable | TP (confirmed) |
| v0.9.3, no `SECRET_KEY` | variant | vulnerable | TP (confirmed) |
| v0.9.5, no `SECRET_KEY` | fixed | not vulnerable (401) | TN |
| v0.9.4, `SECRET_KEY` set (proxy enforced) | benign | not vulnerable (401) | TN |
| other-manifest lookalike | benign | not vulnerable | TN |
| ideon manifest with preview route missing | benign | not vulnerable (404) | TN |

Result: **TP 2 / TN 4 / FP 0 / FN 0 / inconclusive 0** (6 cases). These are
curated fixture results, not a production false-positive rate. No customer
target was contacted.

Limitations:

- A v0.9.4 deployment whose `proxy.ts` enforces a session (a strong
  `SECRET_KEY`/`AUTH_SECRET` and a working NextAuth configuration) answers
  `401` and is not reported. The route itself still has no check, but the
  anonymous relay is not reachable in that configuration.
- The confirmed path requires the app to serve the scanned port directly over
  HTTP, as the default self-hosted `:3000` deployment does. Behind a
  TLS-terminating reverse proxy or on a non-default internal port, the
  loopback URL may not reach the listener; the detector then emits no finding
  rather than claiming a confirmed fetch.
- The release document is read from `/api/system/current-version` only when the
  proxy allows it. When the version is unavailable the detector still relies
  on the observed behavior; a 0.9.5 deployment is protected by the route-level
  `401` even without the version read.

## Reproduce the validation

```shell
pytest tests/exploits/ideon_link_preview_ssrf_test.py tests/exploits/cve_2026_68507_test.py
```

### Run the detector in a scan

```shell
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-68507"]' link --url https://<your-ideon-instance>
```

Filter it with the `custom_cve_list` scanner setting; see
[the README "Run selected CVEs" section](../README.md#run-selected-cves).
The detector ships as part of the Asteroid agent and uses only anonymous
HTTP(S) requests.
