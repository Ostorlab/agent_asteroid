# JeecgBoot OpenAPI OPTIONS authentication bypass (CVE-2026-126998)

## Summary

JeecgBoot's OpenAPI dispatcher (`/openapi/call/{path}`) is guarded by
`ApiAuthFilter`, which checks the caller IP whitelist, the appkey/signature
pair and the per-interface permission row. Up to and including 3.9.5, the
filter forwarded every HTTP `OPTIONS` request to the application chain before
any of those checks. `OpenApiController#call` accepts `OPTIONS`, resolves a
relative `originUrl` against a base URL derived from the request `Host`
header (after `checkInternalUrl` restricts it to loopback, private and
link-local addresses) and proxies the request with a freshly minted
administrative JWT.

The shipped database dump seeds the OpenAPI route `TEwcXBlr`
(`/sys/user/queryUserByDepId`), the public demo appkey
`ak-pFjyNHWRsJEFWlu6` and a matching permission row. A default installation
therefore answers an unauthenticated `OPTIONS` request with the admin-only
user query result. The same primitive can reach other loopback/private
listeners, and a listener there can capture the generated JWT.

The advisory also describes a forged-signature variant in 3.9.2/3.9.3 that
sends the generated JWT to an external `Host`. This module does not exercise
or claim that variant; it deliberately keeps the proxy target on loopback.

## Detection contract

1. Attribute JeecgBoot from an anonymous `GET /jeecg-boot/sys/version/app3version`
   (or the same path at the root for a microservice deployment): HTTP 200
   `application/json`, `success: true`, and a `result` object carrying the
   product app-version schema (`id`, `appVersion`, `versionNum`,
   `downloadUrl`, `webDownloadUrl`, `updateNote`), with at least one
   non-empty download location.
2. Send one anonymous
   `OPTIONS /jeecg-boot/openapi/call/TEwcXBlr?id=c6d7cb4deeac411cb3384b1b31278596`
   with `Host: 127.0.0.1:<observed port>` and the public seeded demo appkey,
   and with no `signature`, `timestamp`, `Origin`, cookie or real credential.
3. Require HTTP 200 JSON with `success: true` and a `result` list containing
   at least one object with a non-empty string `username` and `id`. Only the
   record count is retained; the field values are not stored or reported.

A fixed 3.9.6 server answers the same OPTIONS request with an empty 200 CORS
preflight and never enters the business chain. A deployment without the seeded
route returns the filter's 401/404 `Result` failure. A non-JeecgBoot
application fails the product attribution.

The response body of the self-proxy is parsed in memory and discarded; the
finding reports only the status, content type and record count.

## Safety

- Anonymous: no real credential, signature, timestamp, session or cookie.
  The appkey is the public demo value shipped in `jeecgboot-mysql-5.7.sql`.
- Loopback only: the `Host` header is `127.0.0.1:<port>`; the server's own
  `checkInternalUrl` restricts the target to internal addresses and the
  proxied path is the seeded `/sys/user/queryUserByDepId` read route.
- No token replay: the generated administrative JWT is never read from the
  response or reused.
- No external destination, cloud metadata, file read, command endpoint,
  configuration endpoint or credential endpoint is requested.
- No user-visible state change: the proxied request is a read. The server
  mints a short-lived Redis token for the proxied request; it expires after
  60 seconds and is not used. The OPTIONS short-circuit returns before the
  filter's access-log branch.

## Reproduction

```sh
# fixture (vulnerable)
mvn -B -DskipTests -pl jeecg-module-system/jeecg-system-start -am package
java -jar jeecg-system-start-3.9.5.jar \
  --spring.profiles.active=dev --spring.flyway.enabled=false

# independent oracle and registered detector
python3 oracle.py 127.0.0.1 8080
PYTHONPATH=. python3 validate_detector.py --manifest cases.json
```

The fixture requires MySQL/MariaDB and Redis on their default loopback ports
and the tag's seed SQL loaded into a `jeecg-boot` database. See the artifact
for the full setup and the synthetic-data variant SQL.

## Limitations

- The check is plain HTTP only. A loopback HTTPS self-proxy would face the
  server's own certificate validation, so an HTTPS-only deployment is not
  reported.
- The default seed route and appkey are required. A deployment that changed
  either the OpenAPI path, the demo appkey or the seeded permission row is not
  reported; the check is an exposure check for the default installation.
- A reverse proxy that rewrites `Host`, blocks loopback self-requests or
  answers OPTIONS itself produces no finding.
- A deployment whose root department or admin user was removed returns a
  non-success/empty result and is not reported.
- The detector reports the observed unauthenticated dispatch and admin-record
  read; it does not attempt command execution, JWT capture at another
  listener, or the 3.9.2/3.9.3 external-Host variant.

## Generic handoff (not closed by this module)

The reusable pattern is an HTTP `OPTIONS` preflight that skips an
authorization filter and reaches a business controller that trusts a
request-derived base URL, plus the broader "authentication bypass by method
short-circuit" and "trusted Host used for a server-side request" classes. It
belongs to the General Rule Creator; this CVE module does not claim generic
coverage. The forged-signature variant in the same advisory is a separate
signature-verification weakness (predictable `md5(ak + sk + timestamp)` with
a shipped demo key) and is also a General Rule Creator handoff.
