# Bolo CVE-2026-129493 article view-password disclosure

**CVE-2026-129493** is an unauthenticated information disclosure in Bolo
(`bolo-solo`), a Java blog system derived from Solo. Versions 1.7 through
2.6.4 return the plaintext `articleViewPwd` field of published articles from
the public `GET /articles` JSON endpoint (CWE-200, CVSS 3.1 7.5
`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`, CVSS 4.0 8.7).

The field is the password used to gate a protected article's content, and the
same response also carries the article body, so the view password is not an
effective access control on the API.

No fixed release existed at disclosure.

Checked 16 November 2026 against commit `4ca5a6b` on `main`.

## How does the detector verify the disclosure?

1. Read `GET /` and require an HTML home page carrying a Bolo marker: the
   `bolo-solo` project link in the default footer or a `/skins/bolo-` skin
   path. A non-Bolo site stops here.
2. Read `GET /articles` and require the Bolo/Solo JSON envelope: HTTP 200,
   `Content-Type: application/json`, `sc == true`, an `rslts.pagination`
   object with an integer `paginationPageCount`, and an `rslts.articles`
   array whose first row has string `oId`, `articleTitle`, `articlePermalink`
   and `articleViewPwd` fields. A lookalike JSON body without that shape is
   rejected.
3. Report only when at least one listed article has a non-empty
   `articleViewPwd` string and a non-empty string `oId`. An empty password is
   not a disclosure.
4. Follow the public `?p=N` paging for at most five pages (the first page
   reports `paginationPageCount`), so a protected article on a later page is
   found without an unbounded walk.

Only anonymous `GET` requests are sent. The detector never submits a
password, requests a protected article page, sends a credential or cookie, or
changes state. The leaked password value is never copied into the finding;
the evidence names the article `oId` and the page only.

## What does a positive finding claim?

The finding confirms that the anonymous `/articles` response returned a
non-empty plaintext `articleViewPwd` for a published article. It does not
claim that the article body was read through a password prompt: the same
response already carries `articleContent`, which is why the view password is
not an effective access control on this endpoint. A fixed build that removes
`articleViewPwd` from the response, or a deployment that protects
`GET /articles`, is not reported.

## What does the detector miss?

- A Bolo site whose custom theme removes both the `bolo-solo` footer link and
  the `/skins/bolo-` path is not attributed. That is a false negative, not a
  false positive.
- A protected article on page six or later is not reached because the walk is
  bounded at five pages.
- A site that returns a non-200 home page (for example a canonical-host
  redirect) is not attributed; redirects are not followed.
- A deployment that protects `/articles` with a 401/403 is not reported even
  if a protected article exists, because the anonymous disclosure is not
  observable.
- Network errors, timeouts, truncated or oversized bodies and malformed JSON
  are inconclusive; a missing finding is not proof that the target is
  protected.

## How do I remediate while there is no fixed release?

Until upstream ships a release that drops `articleViewPwd` from the public
response, make the same change as `fixed_app.patch`: add `articleViewPwd` to
the `/articles` request `excludes` list in
`ArticleProcessor.getArticlesByPage`, immediately before
`articleQueryService.getArticles(...)`:

```java
// import org.json.JSONArray;
requestJSONObject.put(
    Keys.EXCLUDES, new JSONArray().put(Article.ARTICLE_VIEW_PWD));
```

The response then omits the field before serialization. If a code change is
not possible, block or restrict anonymous `GET /articles` at the WAF or
reverse proxy while keeping the public article pages reachable. Treat every
article view password as compromised and change it, and review access logs
for anonymous `/articles` requests that enumerated the article list.

## How was the detector validated?

Real upstream tags `v2.6.4_stable` (`e0ab6b1`) and `v2.6.1_stable`
(`0bc4fc6`) were built with Temurin JDK 8u512-b09 and Maven 3.8.5 from the
`ci` profile, then run with the embedded Jetty and an H2 1.4.199 database.
Each fixture was initialised through the product's own `POST
/oauth/bolo/login` first-run flow, and a password-protected article was
created through the authenticated `POST /console/article/` console route.
The fixed control is the same 2.6.4 build with a local patch that adds
`articleViewPwd` to the `/articles` request `excludes` list
(`fixed_app.patch`). An independent stdlib `http.client` oracle, which never
imports the detector, establishes the ground truth; the registered
`CVE2026129493Exploit` ran from a separate client.

| Port | Fixture | Oracle | Detector | Result |
| ---: | --- | --- | --- | --- |
| 18080 | Bolo 2.6.4, protected article `FixtureViewPwd-9f3a` | home Bolo, 1 protected article | 1 finding | TP |
| 18081 | Bolo 2.6.1, protected article `VariantViewPwd-3a1c` | home Bolo, 1 protected article | 1 finding | TP (variant) |
| 18082 | Bolo 2.6.4 with `fixed_app.patch` | `articleViewPwd` absent | no finding | TN (fixed) |
| 18083 | Bolo 2.6.4, default article only | no protected article | no finding | TN (benign) |
| 18084 | Non-Bolo home page with a Bolo-shaped protected JSON | no Bolo marker | no finding | TN (benign) |
| 18085 | Bolo home page, `/articles` answers 401 | article list protected | no finding | TN (benign) |
| 18086 | Bolo home page, `articleViewPwd` is an integer | no string password | no finding | TN (benign) |

Result: **TP 2 / TN 5 / FP 0 / FN 0 / inconclusive 0** (7 real cases). These
are curated fixture results, not a production false-positive rate. No
customer target was contacted.

## How do I reproduce the disclosure locally?

```sh
# 2.6.4 vulnerable fixture
git clone --depth 1 --branch v2.6.4_stable https://github.com/bolo-blog/bolo-solo.git bolo
cd bolo
export JAVA_HOME=~/jdk8u512-b09
export PATH="$JAVA_HOME/bin:$HOME/apache-maven-3.8.5/bin:$PATH"
mvn -q -B package -DskipTests -Pci
cd target/bolo        # the exploded webapp produced by the ci profile
# point the packaged app at an isolated H2 database (WEB-INF/classes/local.properties):
#   runtimeDatabase=H2
#   jdbc.username=root
#   jdbc.password=123456
#   jdbc.driver=org.h2.Driver
#   jdbc.URL=jdbc:h2:/tmp/bolo-data/db;MODE=MYSQL
java -cp 'WEB-INF/lib/*:WEB-INF/classes' org.b3log.solo.Starter \
  --listen_port=18080 --server_port=18080 --server_host=127.0.0.1 \
  --server_scheme=http --runtime_mode=PRODUCTION
# first call performs the first-run initialisation; the second logs in and
# saves the session cookie to /tmp/cj
curl -s -X POST http://127.0.0.1:18080/oauth/bolo/login \
  --data 'username=admin&password=Secret123!'
curl -s -c /tmp/cj -X POST http://127.0.0.1:18080/oauth/bolo/login \
  --data 'username=admin&password=Secret123!'
curl -s -b /tmp/cj -H 'Content-Type: application/json' \
  -X POST http://127.0.0.1:18080/console/article/ \
  --data '{"article":{"articleTitle":"Protected fixture article","articleAbstract":"abstract","articleContent":"<p>secret</p>","articleTags":"fixture","articleStatus":0,"articleCommentable":true,"articleViewPwd":"FixtureViewPwd-9f3a","postToCommunity":false}}'
# the leaked plaintext password is visible in the anonymous response
curl -s http://127.0.0.1:18080/articles
curl -s http://127.0.0.1:18080/articles \
  | grep -o '"articleViewPwd":"[^"]*"'
```

The validation harness (`oracle.py`, `adapter.py`, `cases.json`) and the
fixed patch live in `artifacts/asteroid/2026-11-16-bolo-articles-password/`
in the shared memory repository.
