# LibreNMS CVE-2026-86426 API token type confusion

**CVE-2026-86426** is an authentication bypass (CWE-287) in LibreNMS before
26.8.0. The REST API validates a submitted token against stored token hashes
using MySQL's loose type coercion, so a numeric `api_token` such as `0`
through `9` can match a stored hash, letting an unauthenticated attacker
reach protected endpoints without a real token.

**Affected:** LibreNMS before 26.8.0

**Fixed:** 26.8.0

**Severity:** CVSS 3.1 9.8 (Critical) — `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`

## How does the detector verify it?

This is an **active, non-destructive** check. It confirms the product with
an anonymous homepage read, then tries each digit `0`-`9` as the token of a
single bounded read:

```
GET  /                                            # confirm LibreNMS
POST /api/v0/devices   {"api_token": <0..9>}      # type confusion match -> device inventory
```

A match is reported only when a numeric token returns HTTP 200 JSON device
inventory AND a second request carrying a random non-numeric token
(`secrets.token_hex(8)`) is confirmed refused (non-200) — this differential
control rules out deployments whose API answers any request without
authentication. No token beyond the ten digits the flaw itself exploits is
tried (plus the single random control token), no data is written, and
redirects are not followed.

**Limitation:** the check only tries the digits `0` through `9`, the same
guesses the public advisory documents as sufficient to trigger the type
coercion; a deployment whose stored token hashes never coerce to one of
those ten integers produces no match and is not reported.

## Remediation

Update LibreNMS to version 26.8.0 or later. Restrict network access to the
LibreNMS API to trusted clients.
