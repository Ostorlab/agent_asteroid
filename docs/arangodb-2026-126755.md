# CVE-2026-126755: ArangoDB URL-encoded-underscore authentication bypass

**CVE-2026-126755 is an unauthenticated authentication bypass** in ArangoDB
(CWE-288, CVSS 3.1 9.8). The authorization gate decides whether a request may
proceed without credentials from the *raw* request path, while the action
dispatcher resolves the *URL-decoded* path. Encoding the leading underscore of
a privileged system route as `%5f` makes the request look like a public Foxx
route to the gate, but the dispatcher still runs the real `_api/*` action with
superuser rights.

**Affected:** ArangoDB <= 3.12.10.1

**Fixed:** 3.12.11

**Severity:** CVSS 3.1 9.8 (Critical) —
`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`; CVSS 4.0 9.3

The advisory reports exploitation evidence observed by the Shadowserver
Foundation on 2026-09-16 and a public proof of concept since 2026-09-13. The
bypass applies with the default `--server.authentication-system-only true` on
single-server and coordinator roles with Foxx enabled.

## How does the detector verify the bypass?

1. `PUT /_db/_system/_api/simple/first-example` without credentials must answer
   HTTP 401 with ArangoDB's own challenge: the `Server` header contains
   `ArangoDB`, or `WWW-Authenticate` carries `realm="ArangoDB"`. This attributes
   the product and proves the canonical privileged path requires
   authentication.
2. The same anonymous request at
   `PUT /_db/_system/%5fapi/simple/first-example` must answer HTTP 404 with
   ArangoDB's own action error for the random, non-existent collection supplied
   in the body: `error` is `true`, `errorNum` is `1203`, and `errorMessage`
   names that collection. Reaching the action's missing-collection error proves
   the privileged JavaScript action was dispatched as superuser without
   credentials. A fixed 3.12.11 server answers HTTP 401 exactly like the
   control; a server started with `--server.authentication-system-only false`
   also answers 401.

The check sends only two anonymous PUTs. The action is a read action and the
collection name is random and cannot exist, so no collection or document is
read, created, modified or deleted.

## What does a positive finding claim?

The finding confirms the parser differential: the encoded request reached the
privileged `_api/simple/first-example` action without credentials while the
canonical request was refused. It does not claim that any document was read,
modified or deleted; the advisory's read/write impact (including the `_users`
password hashes) was deliberately not exercised. Because the same gate protects
every `_api/simple/*` action, the confirmed dispatch is the CVE's
authentication-bypass primitive.

## What does the detector miss?

- A deployment with authentication disabled entirely
  (`--server.authentication false`) answers the control with the action result
  rather than 401, so it is not reported; such a deployment is already
  unauthenticated by configuration, not by this parser differential.
- A deployment with `--server.authentication-system-only false` is the
  documented mitigation and answers 401 on the encoded path; the detector
  correctly leaves it unreported, but the underlying release may still be old.
- A reverse proxy that authenticates, blocks or rewrites
  `/_db/_system/_api/simple/first-example` or the encoded path prevents the
  finding, even if the backend build is vulnerable.
- A deployment that mounts ArangoDB under a path prefix is not probed; the
  check uses the origin's standard paths.
- A deployment that strips both the `Server` header and the ArangoDB
  `WWW-Authenticate` realm from the 401 challenge loses the primary attribution
  signals for the control. The encoded 404 may still be accepted as ArangoDB
  provenance when it carries the `X-Arango-Queue-Time-Seconds` header and the
  exact error shape; if those are stripped too, the result is inconclusive.
- Network errors, timeouts, truncated responses and unsupported schemes are
  inconclusive and produce no finding; a missing finding is not proof that the
  bypass is absent.

## How do I run the check?

```sh
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-126755"]' ip 10.0.0.10
```

The equivalent manual differential on the same origin is:

```sh
curl -i -X PUT 'http://<target>:8529/_db/_system/_api/simple/first-example' \
  -H 'Content-Type: application/json' \
  -d '{"collection":"asteroid-probe","example":{}}'
curl -i -X PUT 'http://<target>:8529/_db/_system/%5fapi/simple/first-example' \
  -H 'Content-Type: application/json' \
  -d '{"collection":"asteroid-nonexistent","example":{}}'
```

| Request | Vulnerable | Mitigated / fixed |
| --- | --- | --- |
| canonical `_api` | `401` ArangoDB challenge | `401` ArangoDB challenge |
| encoded `%5fapi` | `404` `errorNum 1203` unknown collection | `401` ArangoDB challenge |

The check sends two anonymous PUTs and no other request.

## How do I fix CVE-2026-126755?

Upgrade ArangoDB to 3.12.11 or later, which decodes the path before the
authorization decision. If an upgrade cannot be applied immediately, start
`arangod` with `--server.authentication-system-only false` so every route,
including Foxx routes, requires authentication, and restrict the HTTP endpoint
to trusted clients. If an affected deployment was reachable by untrusted
clients, treat its data as exposed: rotate the `root` password and every
database user password, rotate the JWT secret or keyfile, and review the
server and web-interface access logs for paths containing `%5f` or for
unauthenticated `_api/simple/*` requests.

## How was the detector validated?

Real ArangoDB releases were run on loopback:

- ArangoDB 3.12.10 enterprise (official image files) — vulnerable.
- ArangoDB 3.12.4 community (official Linux tarball) — vulnerable variant.
- ArangoDB 3.12.11 enterprise (official image files) — fixed.
- ArangoDB 3.12.10 behind a TLS terminator over `https` — vulnerable.
- ArangoDB 3.12.10 with `--server.authentication-system-only false` —
  documented mitigation.

An independent standard-library oracle performed the same two requests and
recorded the raw statuses and bodies; the registered detector was exercised
from a separate client. A stdlib lookalike returned a generic 401/404 pair
without ArangoDB provenance.

| Case | Build | Detector | Oracle |
| --- | --- | --- | --- |
| 1 | 3.12.10 | TP: 404 `errorNum 1203` | vulnerable |
| 2 | 3.12.4 | TP: 404 `errorNum 1203` | vulnerable |
| 3 | 3.12.10 over `https` | TP: 404 `errorNum 1203` | vulnerable |
| 4 | 3.12.11 | TN: 401 on both | fixed |
| 5 | 3.12.10, system-only false | TN: 401 on both | mitigated |
| 6 | generic 401/404 lookalike | TN | not the product |
| 7 | ArangoDB-shaped 404 lookalike, no provenance | TN | not the product |

**TP 3 / TN 4 / FP 0 / FN 0 / inconclusive 0** on the seven real or independent
fixtures. The focused mocked suite additionally covers authentication-disabled
deployments, a wrong `errorNum`, a collection name that is not echoed, a
proxy-stripped `Server` header, fixed and mitigated builds, and non-ArangoDB
lookalikes.
