# CVE-2026-110003: Payara Server arbitrary auth-token remote-admin bypass

**CVE-2026-110003 is a remote administration authentication bypass** in Azul
Payara Server (CWE-288, CVSS 4.0 9.3). When the administration REST interface
has secure admin disabled, Payara rejects requests from a remote peer. Before
the FISH-14855 fix, the authenticator accepted *any* non-null
`X-GlassFish-authToken` header as proof of a trusted instance start-up and
skipped that rejection **before** validating the token. The request then fell
through to password authentication, which accepts the default administrative
account with an empty password on a default domain.

**Affected:** 7.0.0 < 7.6.0; 7.2024.1.Alpha1 < 7.2026.11; 6.0.0 < 6.44.0;
6.2022.1 <= 6.2025.11; 5.20.0 < 5.93.0; 5.181 <= 5.201.2; 5.2020.2 <=
5.2022.5; 4.1.2.191 < 4.1.2.191.61

**Fixed:** 7.2026.11, 7.6.0, 6.44.0, 5.93.0, 4.1.2.191.61 (commit `9192e369`,
FISH-14855)

**Severity:** CVSS 4.0 9.3 (Critical) — `AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N`

The fix changes the check from `cbh.tkn() != null` to
`cbh.tkn() instanceof String token && authTokenManager.findToken(token) != null`,
so only a token the one-time token manager actually issued waives the remote
rejection. The default domain of the shipped distribution also accepts the
administrative account with an empty password; a deployment with a strong
administrative password still exposes the remote-access restriction bypass,
but not administrative access.

## How does the detector verify the bypass?

1. `GET /management/domain/version` without a token must answer HTTP 403
   `application/json` with the Payara administration error:
   `exit_code` is `FAILURE`, `command` is `Error`, and `message` contains
   `Remote access not allowed`. This proves the interface is Payara and that
   secure-admin remote access is disabled.
2. The same anonymous request with a locally generated, non-existent
   `X-GlassFish-authToken` must either:
   - answer HTTP 200 with the successful `version AdminCommand` document
     (`exit_code` `SUCCESS`, `message` contains `Payara Server`), which proves
     unauthenticated administrative access; or
   - answer HTTP 401 with a `Basic` challenge and the Payara
     `Invalid user name or password` error, which proves the remote-access
     bypass but not administrative access.

Payara is attributed from the `Server` response header (`Payara Server
7.2026.10`); when a proxy strips it, the standard administration console title
(`Payara Server Administration Console`) is used instead. A fixed server
answers HTTP 403 to the second request exactly like the control.

The token is random (`asteroid-<uuid>`) and is not a credential. The check
sends two anonymous GETs and reads only the version document. It never requests
`/management/domain`, a configuration, resource or credential document, and it
changes no state.

## What does a positive finding claim?

The 200 case confirms that an unauthenticated remote client can execute the
administrative `version` command, because the arbitrary header bypassed the
secure-admin restriction and the default empty administrative password was
accepted. The finding does not claim that a state-changing administrative
command was executed; only the read-only `version AdminCommand` was run.

The 401 case confirms that the remote-access restriction was bypassed (the same
request without the header is refused with 403) but that the deployment
requires a non-default administrative password, so administrative command
execution was not obtained. This is the same CVE and the same vulnerable code
path, with the documented impact precondition.

## What does the detector miss?

- A deployment with secure admin enabled answers the control request with 401
  or 200, not the 403 remote rejection; it is not reported because the remote
  restriction is not active.
- A reverse proxy that authenticates, blocks or strips
  `/management/domain/version` produces no finding, even if the backend build
  is vulnerable.
- A Payara installation whose administration console and REST interface are
  mounted under a path prefix is not probed; the check uses the origin's root
  paths.
- A deployment with a non-default administrative password is reported only as
  the restriction bypass, not as administrative access.
- Network errors, timeouts, truncated responses and unsupported schemes are
  inconclusive and produce no finding; a missing finding is not proof that the
  bypass is absent.
- A build that contains the FISH-14855 fix returns the same 403 as the control
  and produces no finding, even if an unrelated administrative weakness exists.

## How to reproduce and remediate

The differential on the same origin is:

```sh
curl -i 'http://<target>:4848/management/domain/version'
curl -i -H 'X-GlassFish-authToken: asteroid-probe' \
  'http://<target>:4848/management/domain/version'
```

| Request | Vulnerable (empty admin password) | Vulnerable (non-default password) | Fixed |
| --- | --- | --- | --- |
| no token | `403` `Remote access not allowed` | `403` `Remote access not allowed` | `403` `Remote access not allowed` |
| random token | `200` `version AdminCommand` | `401` + `WWW-Authenticate: BASIC` + `Invalid user name or password` | `403` `Remote access not allowed` |

Upgrade to 7.2026.11 (or 7.6.0), 6.44.0, 5.93.0 or 4.1.2.191.61. Set a strong
administrative password so the empty default cannot be used, restrict network
access to the administration port (4848 by default) to trusted management
hosts, and enable secure admin only if remote administration is required.
After the upgrade, confirm that both requests return the `Remote access not
allowed` rejection. Review the server's audit and access logs for
administrative commands from untrusted hosts if an earlier build was exposed,
and rotate administrative credentials. For the agent-side summary, run
`oxo vulnz describe -v CVE-2026-110003`.

## How was the detector validated?

Real Azul Payara Community 7.2026.10 (vulnerable) and 7.2026.11 (fixed)
distributions were downloaded from Maven Central
(`fish.payara.distributions:payara`) and their SHA-1 values checked against the
repository metadata. Each was run on Temurin JDK 21 in an isolated QEMU guest
with user-mode networking, so the administration interface saw the client as a
remote peer (`10.0.2.2`) rather than a same-host loopback address, which Payara
treats as local. The registered detector was exercised from a separate network
client against the forwarded administration port. An independent
standard-library oracle performed the same two requests and recorded the raw
statuses and JSON bodies.

| Case | Build | Admin password | Detector | Oracle |
| --- | --- | --- | --- | --- |
| 1 | 7.2026.10 `domain1` | default empty | TP: 200 `version AdminCommand` | vulnerable |
| 2 | 7.2026.10 `locked` | non-default | TP: 401 Basic + `Invalid user name or password` | bypass only |
| 3 | 7.2026.11 `domain1` | default empty | TN: 403 on both requests | fixed |
| 4 | non-Payara lookalike (`Server: nginx`, Payara-shaped bodies) | — | TN | not the product |

**TP 2 / TN 2 / FP 0 / FN 0 / inconclusive 0** on the four real fixtures. The
focused mocked suite additionally covers the secure-admin-enabled control
(`401`), a proxy that strips the token header, redirects, malformed bodies,
transport failures and unsupported schemes. The finding carried
the expected title, CRITICAL rating, version evidence (when the version command
succeeded), references and DNA; no credential or configuration document was
read.
