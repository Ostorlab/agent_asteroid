# DeepAudit CVE-2026-129877 configuration-secret disclosure

**CVE-2026-129877** is an unauthenticated information disclosure in DeepAudit,
a self-hosted AI code-audit platform. Versions 2.0.0-beta.1 through 3.8.0
expose `GET /api/v1/config/defaults` without an authentication dependency
(CWE-306, CVSS 3.1 7.5 `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`, CVSS 4.0 8.7).
The handler returns the backend's default configuration, which includes the
operator's provider API keys (`openaiApiKey`, `geminiApiKey`, `claudeApiKey`
and the other per-provider fields) and the global `githubToken` and
`gitlabToken`.

The endpoint is reachable on the backend port (`8000` in the official
compose) and through the frontend nginx `/api/` proxy, so an anonymous
visitor can read the configured credentials and use them against the linked
LLM, GitHub or GitLab account. The exposure requires at least one provider key or
Git token to be configured on the server.

No fixed release existed at disclosure.

## How does the detector verify the disclosure?

1. Read `GET /` and require a DeepAudit root document: the backend JSON
   welcome document (`message == "Welcome to DeepAudit API"` and
   `docs == "/docs"`) or the frontend HTML page with
   `<title>DeepAudit</title>`. A lookalike application stops here.
2. Read `GET /api/v1/config/defaults` and require HTTP 200,
   `Content-Type: application/json`, and the exact defaults document shape:
   an `llmConfig` object with string `llmProvider`, string `llmModel`,
   integer `llmTimeout`, string `ollamaBaseUrl`, and an `otherConfig` object
   with integer `maxAnalyzeFiles`, integer `llmConcurrency`, integer
   `llmGapMs` and string `outputLanguage`. A generic config document without
   that shape is rejected.
3. Collect the documented secret fields: the ten per-provider
   `*ApiKey` fields and `githubToken`/`gitlabToken`. The generic `llmApiKey`
   is not included because the upstream defaults handler hard-codes it to an
   empty string. Report only when at least one field carries a non-empty
   string of at least eight characters that is not an obvious documentation
   placeholder (`your-`, `changeme`, `placeholder`, `example`, `dummy`).
4. Never retain or emit the secret value. The finding names the exposed
   fields and the non-secret `llmProvider` value only.

Only anonymous `GET` requests are sent. The detector never sends a
credential or cookie, never submits a request body, and changes no state.

## What does a positive finding claim?

The finding confirms that the anonymous defaults endpoint returned a
non-empty value for at least one documented server-side secret field. It does
not claim that the value is a live credential; the operator must confirm and
rotate it. A build that requires authentication for the endpoint, a
deployment that redacts the secret fields, a deployment with no provider key
or Git token configured, and a removed endpoint are not reported.

## What does the detector miss?

- A custom frontend that changes the `<title>DeepAudit</title>` text and a
  reverse proxy that strips the backend JSON welcome document are not
  attributed. That is a false negative, not a false positive.
- A site that returns a non-200 root page (for example a canonical-host
  redirect) is not attributed; redirects are not followed.
- A deployment whose configured values are documentation placeholders,
  masked displays (`********`), or redacted markers (`[REDACTED]`, `hidden`,
  `masked`) is not reported, because no live secret is exposed. A real key
  whose value happens to contain one of the placeholder markers (`example`,
  `dummy`, ...) is also not reported; the markers are deliberately narrow.
- A field whose value is shorter than eight characters is not reported, so an
  unusually short configured secret is missed; the threshold is a deliberate
  suppression heuristic, not a liveness test.
- A deployment that protects `/api/v1/config/defaults` with a 401/403 is not
  reported even if secrets are configured, because the anonymous disclosure
  is not observable.
- Network errors, timeouts, truncated or oversized bodies and malformed JSON
  are inconclusive; a missing finding is not proof that the target is
  protected.

## How do I remediate while there is no fixed release?

Require an authenticated administrator for `GET /api/v1/config/defaults`, or
remove the endpoint and keep server secrets out of API responses. Do not
publish provider API keys or Git tokens to the browser. Restrict the backend
port `8000` to the frontend network and protect `/api/` with authentication.
Treat every key or token that the endpoint may have returned as compromised
and rotate it, and review access logs for anonymous requests to
`/api/v1/config/defaults`.

## How was the detector validated?

The official compose stack needs Docker, PostgreSQL and Redis, which are not
available in the validation sandbox. The fixture therefore pins the real
upstream backend source at tags `v3.8.0` (`9aa46568`) and `v2.0.0-beta.8`
(`ebfe9fa1`), imports the real
`app.api.v1.endpoints.config` router into a minimal FastAPI host, and
reproduces the upstream `app/main.py` root document verbatim. The frontend
case serves the upstream `index.html` title instead. This exercises the real
handler and settings model without reimplementing the endpoint.

The fixed controls are the same v3.8.0 source with a local patch that adds
`Depends(deps.get_current_user)` to `/defaults` (401), the same source with
the secret fields redacted to empty strings, the same source with masked
(`********`) and `[REDACTED]` displays, and a deployment with no secret
configured. An
independent stdlib `http.client` oracle, which never imports the detector,
establishes the ground truth; the registered `CVE2026129877Exploit` ran from
a separate client.

| Case | Fixture | Oracle | Detector | Result |
| --- | --- | --- | --- | --- |
| `vulnerable-v3.8.0-backend` | v3.8.0, backend JSON root, OpenAI key + GitHub/GitLab tokens | 3 secret fields exposed | 1 finding | TP |

| `benign-removed-endpoint-v3.8.0` | v3.8.0, `/defaults` removed | 404 | no finding | TN (benign) |

Result: **TP 3 / TN 6 / FP 0 / FN 0 / inconclusive 0** (9 real cases). These
are curated fixture results, not a production false-positive rate. No
customer target was contacted.

## How do I reproduce the disclosure locally?

```sh
git clone --depth 1 --branch v3.8.0 https://github.com/lintsinghua/DeepAudit.git deepaudit-v3.8.0
cd deepaudit-v3.8.0/backend
# install the light dependency subset used by the config router
uv venv --python 3.13 /tmp/deepaudit-venv
. /tmp/deepaudit-venv/bin/activate
uv pip install fastapi==0.122.0 uvicorn==0.35.0 pydantic==2.12.4 \
  pydantic-settings==2.13.0 sqlalchemy==2.0.44 asyncpg==0.31.0 \
  'python-jose[cryptography]==3.5.0' 'passlib[bcrypt]==1.7.4' \
  bcrypt==4.3.0 email-validator==2.3.0 python-multipart==0.0.20 \
  cryptography==46.0.0
# save the minimal fixture host in this backend directory
cat > serve.py <<'PY'
from fastapi import FastAPI

from app.api.v1.endpoints import config

app = FastAPI(title="DeepAudit")


@app.get("/")
def root() -> dict[str, object]:
    return {
        "message": "Welcome to DeepAudit API",
        "docs": "/docs",
        "demo_account": {"email": "demo@example.com", "password": "demo123"},
    }


@app.get("/health")
def health() -> dict[str, str]:
    return {"status": "ok"}


app.include_router(config.router, prefix="/api/v1/config")
PY
export PYTHONPATH="$PWD"
export DATABASE_URL='postgresql+asyncpg://fixture:fixture@127.0.0.1:5432/fixture'
export SECRET_KEY='fixture-secret-key-for-validation'
export OPENAI_API_KEY='sk-proj-FixtureAlpha9aQ2Z7'
export GITHUB_TOKEN='ghp_FixtureAlpha9aQ2Z7'
export GITLAB_TOKEN='glpat-FixtureAlpha9aQ2Z7'
python -m uvicorn serve:app --host 127.0.0.1 --port 18080 --log-level warning
# anonymous request, no Cookie or Authorization header
curl -s http://127.0.0.1:18080/api/v1/config/defaults
```

The response carries the synthetic `openaiApiKey`, `githubToken` and
`gitlabToken` values. The full fixture used for validation (including the
authenticated, redacted, masked, no-secret, lookalike and removed-endpoint
controls) lives in the validation artifact; the minimal host above is enough
to reproduce the vulnerable response. The oracle and the registered detector
are run by `validate.py` in that artifact directory; both use only the
exposed HTTP service.
