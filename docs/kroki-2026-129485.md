# Kroki CVE-2026-129485 BlockDiag unauthenticated SSRF

**CVE-2026-129485** is an unauthenticated server-side request forgery in
Kroki, a self-hosted diagram rendering gateway. Before 0.36.0 the BlockDiag
family (`blockdiag`, `seqdiag`, `actdiag`, `nwdiag`, `packetdiag` and
`rackdiag`) passed the diagram source unchanged to the `blockdiag` binary. A
node's `icon` or `background` attribute accepts any URL, and the binary fetches
it with `urllib` while laying out the diagram. `KROKI_SAFE_MODE` never reached
this engine, so an anonymous `POST /blockdiag/svg` (or a sibling route) made
the server request an arbitrary URL (CWE-918, CVSS 3.1 5.8
`AV:N/AC:L/PR:N/UI:N/S:C/C:L/I:N/A:N`, CVSS 4.0 6.9).

An image-returning target's body is embedded in the rendered SVG, giving an
attacker a read channel into internal services that serve images. Non-image
responses, for example cloud metadata JSON, cannot be embedded; the fetch is
confirmed only through the renderer's error, which names the exact URL. The
same attributes also accept a local path, which `blockdiag` reads. Kroki 0.36.0
fixes the default by shipping blockdiag 3.4.3 and passing its
`--no-external-images` flag unless `KROKI_SAFE_MODE=unsafe`.

Checked 16 November 2026. Baseline `59bf7d7` on `main`.

## How does the detector verify the SSRF?

1. Read `GET /health` and require the Kroki health document: HTTP 200,
   `Content-Type: application/health+json`, `status` `pass`, a parseable
   `version.kroki.number` below 0.36.0, and a parseable `version.blockdiag`
   label. A release label that is missing, open-ended or a pre-release
   (`0.36.0-SNAPSHOT`) fails closed.
2. Send the control diagram `blockdiag { A -> B; }` to
   `POST /blockdiag/svg` as `text/plain` and require HTTP 200 with an
   `image/svg+xml` body. A missing, protected or non-rendering BlockDiag route
   is not reported.
3. Send a second diagram with `A [icon = "http://127.0.0.1:<observed-port>/<random>"]`.
   The path is synthetic and does not exist. The vulnerable renderer fetches
   it, fails to decode the response and returns HTTP 400 with the BlockDiag
   fetch error naming that exact URL (`Could not retrieve` or
   `unknown image type`). If the synthetic path happens to return an image,
   the vulnerable renderer returns HTTP 200 with the bytes embedded as
   `data:;base64,`; the detector accepts that form too.
4. A 0.36.0-or-later release, a control that does not render, a generic 400
   that does not name the exact probe URL or does not carry a BlockDiag error
   marker, a 200 SVG without an embedded image, a redirect, a timeout and a
   transport error all produce no finding.

Only three anonymous requests are sent. The server is asked only to fetch a
non-existent path on its own loopback port; the detector never asks it to
contact another internal service, a cloud metadata endpoint, a local file or a
third-party host, and it changes no state.

## What does a positive finding claim?

The finding confirms that the anonymous BlockDiag renderer fetched the exact
caller-named loopback URL. It does not claim that an internal body, a cloud
metadata credential or a local file was read: the probe path is synthetic and
returns nothing. The advisory's internal-service and local-file impact follows
from the same fetch primitive; the detector deliberately leaves it unexercised.

## What does the detector miss?

- A deployment that hides `/blockdiag/svg` behind a reverse proxy but leaves
  `/seqdiag`, `/actdiag`, `/nwdiag`, `/packetdiag` or `/rackdiag` reachable is
  not reported by this version of the check. The six routes share the same
  vulnerable engine on a stock image.
- The loopback probe uses the observed port. A deployment whose renderer
  cannot reach its own loopback port in any form (for example a
  network-namespace or policy that rejects the connection) still proves the
  fetch attempt, because the BlockDiag error names the URL; a proxy that
  fabricates a 200 image for that path is accepted as the embedded-image form.
- Kroki 0.36.0 or later running with `KROKI_SAFE_MODE=unsafe` still fetches,
  but the release is outside the CVE's affected range, so the detector does
  not report it as CVE-2026-129485. That is a deliberate configuration, not
  the fixed default.
- A patched older release that passes `--no-external-images` itself, or a
  wrapper that ignores icon URLs, is not reported because the behaviour probe
  sees no fetch. This is the intended fail-closed direction.
- Network errors, timeouts, truncated or oversized bodies and unsupported
  schemes are inconclusive; a missing finding is not proof that the target is
  protected.

## How was the detector validated?

Real upstream standalone releases 0.35.0, 0.33.0 and 0.36.0 were run from the
signed release jars with Temurin JDK 21.0.13+9 and the real blockdiag 3.4.2 and
3.4.3 Python packages. An independent stdlib oracle starts its own loopback
listener, asks the BlockDiag route to fetch a URL on that listener, and uses
the observed request as ground truth; it never imports the detector. The
registered `CVE2026129485Exploit` ran from a separate client.

| Port | Fixture | Oracle | Detector | Result |
| ---: | --- | --- | --- | --- |
| 18035 | Kroki 0.35.0, blockdiag 3.4.2, default config (`KROKI_SAFE_MODE` unset) | fetch observed, release <0.36.0 | 1 finding | TP |
| 18037 | Kroki 0.33.0, blockdiag 3.4.2, default config | fetch observed, release <0.36.0 | 1 finding | TP (variant) |
| 18039 | Kroki 0.35.0, blockdiag 3.4.3, default config (0.35.0 does not pass the flag) | fetch observed, release <0.36.0 | 1 finding | TP (variant) |

| 18038 | Kroki 0.36.0, blockdiag 3.4.3, `KROKI_SAFE_MODE=unsafe` | fetch observed, release 0.36.0 | no finding | TN (out of CVE range) |
| 18041 | HTML `/health` lookalike | no Kroki health document | no finding | TN (benign) |

## Generic path (not closed by this detector)

An unauthenticated diagram/rendering service that fetches a caller-named URL
from a diagram attribute is the same reusable weakness as the existing
self-referential loopback URL-fetch handoffs (Wanderer CVE-2026-71495, ideon
CVE-2026-68507 and bukuserver CVE-2026-123201). The General Rule Creator owns
the discovery and generic probe; this CVE module does not claim generic
coverage.
