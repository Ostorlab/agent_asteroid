# CVE-2026-127279: ACPs-community discovery-server unauthenticated management API

**CVE-2026-127279 is a missing-authentication vulnerability** in the AIP-PUB
ACPs-community discovery server (CWE-306, CVSS 3.1 7.3). Through v2.2.0,
`discovery-server/app/main.py` mounts management routers on the public FastAPI
listener (port 9005 by default) without any authentication dependency.

v2.2.0 mounts both `/admin/dsp` and `/admin/alive-sync`; v2.1.0 mounts only
`/admin/dsp`:

```python
app.include_router(dsp_router, prefix="/admin/dsp", ...)
app.include_router(alive_sync_router, prefix="/admin/alive-sync", ...)
```

The exposed routes mix read-only state and destructive operations. `POST
/admin/dsp/hard-reset` truncates the agent data, `POST /admin/dsp/stop`
disables background synchronisation, and `POST /admin/dsp/reset` / `POST
/admin/dsp/sync` force expensive full-sync cycles. `GET /admin/dsp/status` and
`GET /admin/dsp/registry-info` expose the synchronisation state and the
registry connection configuration (the status document includes `registry_url`;
any embedded userinfo is redacted in the finding).

Upstream issue #12 documents
the missing dependency and a reproduction; no fixed release existed at
disclosure.

**Affected:** AIP-PUB ACPs-community through v2.2.0 (and the current main line
at disclosure)

**Fixed:** none at disclosure; issue #12 remains open

**Severity:** CVSS 3.1 7.3 (High) — `AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:L`;
CVSS 4.0 5.5

## How does the detector verify the unauthenticated management API?

1. `GET /openapi.json` must return the FastAPI document with the exact
   `info.title` `Agent Discovery Server`, a release label at or below `2.2.0`,
   and the management route set: `GET /admin/dsp/status`, `POST
   /admin/dsp/start`, `POST /admin/dsp/stop`, `POST /admin/dsp/sync`, `POST
   /admin/dsp/reset` and `POST /admin/dsp/hard-reset`. Version 2.2.0 also
   mounts `/admin/alive-sync`, but it is not required: 2.1.0 is affected and
   mounts only `/admin/dsp`.
2. `GET /admin/dsp/status` on the same origin, with no `Authorization` header
   and no cookie, must answer HTTP 200 with the application's own `DSPStatus`
   document: boolean `is_running` and `needs_snapshot`, an integer-or-null
   `last_seq`, a mapping `object_count_by_type` from object-type names to
   integer counts, an integer `sync_interval` and a non-empty string
   `registry_url`.

The status endpoint is read-only: it re-reads the in-memory sync state, which
the server loaded from the database at startup, and counts object versions. The destructive routes are only observed
in the OpenAPI document; they are never called. A deployment that authenticates
the management routers, or hides them from the network, answers 401, 403 or 404
and is not reported. A different FastAPI application that happens to use the
same route names but a different status contract is not reported.

## What does a positive finding claim?

The finding confirms that an anonymous client can reach the discovery server's
management router and read its status document. Because the same router has no
authentication dependency, any client that can reach the listener can also
invoke the destructive and resource-consuming routes the OpenAPI document
advertises: hard-reset, stop, reset and sync. The detector does not call those
routes, does not delete or modify agent data, does not change the sync state
and does not read a registry credential. The claim is the exposed management
surface and the read-only status disclosure, not a performed destructive
action.

## What does the detector miss?

- A management router that answers 401/403/404 at the scanned URL may still be
  reachable on port 9005 through another route or interface; a clean result
  must be confirmed with a direct request before treating the target as
  protected.
- A deployment that binds the whole service to loopback or an internal network
  is unreachable from the scan and is not reported; the exposure is real but
  not remotely observable.
- A deployment that changes the FastAPI `APP_NAME`, so the OpenAPI title is not
  `Agent Discovery Server`, is not attributed and is inconclusive.
- The check uses the origin's root paths; a deployment mounted under a path
  prefix is not probed.
- Network errors, timeouts, redirects, truncated responses and unsupported
  schemes are inconclusive and produce no finding. A missing finding is not
  proof that the management API is protected.

## How do I reproduce CVE-2026-127279?

The decisive read-only requests are:

```sh
curl -sS 'http://<target>:9005/openapi.json'
curl -i 'http://<target>:9005/admin/dsp/status'
```

| Request | Vulnerable | Fixed (authenticated or hidden) |
| --- | --- | --- |
| `GET /openapi.json` | 200 with the `Agent Discovery Server` document | 200 (attribution still possible) or 401 |
| `GET /admin/dsp/status` | 200 with `DSPStatus` | 401, 403 or 404 |

## How do I remediate CVE-2026-127279?

Add an authentication dependency to both management routers before mounting
them, or remove them from the public listener and reach them only over a
loopback or internal management network. In the interim, restrict port 9005 to
trusted management hosts with a reverse-proxy allow-list and authentication,
and do not publish it in deployment templates.

Review the discovery-server access logs for anonymous calls to
`/admin/dsp/hard-reset`, `/admin/dsp/stop`, `/admin/dsp/reset` or
`/admin/dsp/sync`. If any succeeded, re-sync the agent data. Review the
registry connection configuration returned by `/admin/dsp/status` and
`/admin/dsp/registry-info`; if the configured URL embeds credentials, rotate
them and move them out of the URL. For the agent-side summary, run
`oxo vulnz describe -v CVE-2026-127279`.

## How was the detector validated?

Real upstream revisions were run on loopback against PostgreSQL 16.16.

- **Vulnerable fixtures:** tag `v2.2.0` (`39deceb`), tag `v2.1.0` (`abc68d7`),
  which is affected but mounts only `/admin/dsp`, and the current main line
  (`d7a0a5c`), each with a different synthetic agent seed.
- **Fixed controls:** no upstream fix exists, so the controls are an
  authenticating reverse proxy in front of the same v2.2.0 release and a local
  copy of v2.2.0 with an application-level `Depends` check on both management
  routers.
- **Benign controls:** a FastAPI lookalike with the same title, release and
  route names but a non-`DSPStatus` body; a lookalike with the same route set
  and `DSPStatus` body under a different title; and a proxy that hides the
  management routes (404) while leaving the OpenAPI document visible.
- **Oracle:** an independent standard-library `http.client` oracle established
  ground truth and never imports the detector. The registered
  `CVE2026127279Exploit` ran from a separate client with only the target URL.

| # | Fixture | Oracle | Detector | Result |
| --- | --- | --- | --- | --- |
| 1 | ACPs v2.2.0 (`39deceb`), seeded PostgreSQL | anonymous status 200 | 1 finding | TP |
| 2 | ACPs v2.1.0 (`abc68d7`), only `/admin/dsp`, different seed | anonymous status 200 | 1 finding | TP (variant) |
| 3 | ACPs main (`d7a0a5c`), different seed | anonymous status 200 | 1 finding | TP (variant) |
| 4 | v2.2.0 behind an authenticating proxy | 401 | no finding | TN (fixed) |
| 5 | v2.2.0 with app-level router auth | 401 | no finding | TN (fixed) |
| 6 | FastAPI lookalike, wrong status contract | 200 `{"ok":true}` | no finding | TN (benign) |
| 7 | FastAPI lookalike, different title | 200 `DSPStatus` | no finding | TN (benign) |
| 8 | v2.2.0 behind a proxy hiding `/admin/*` | 404 | no finding | TN (benign) |

**TP 3 / TN 5 / FP 0 / FN 0 / inconclusive 0** (8 cases). The focused mocked
suite additionally covers the 2.1.0 route set without `/admin/alive-sync`, an
empty store, a malformed/duplicate JSON field, a non-JSON OpenAPI body, a
redirect, a missing destructive route, an unparseable release, a 500 status,
transport failures and an unsupported scheme. The detector sends only two
anonymous GETs and no mutation, credential or cookie.
