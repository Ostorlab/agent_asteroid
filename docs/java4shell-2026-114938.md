# Java4Shell (CVE-2026-114938) — potential-exposure detector

## Summary

CVE-2026-114938, named Java4Shell, is a heap out-of-bounds write in OpenJDK
HotSpot's x86-64 AVX-512 VBMI Base64 intrinsic. A malformed padded Base64 tail
makes the decoder calculate a negative output length; the resulting store mask
writes 64 bytes where almost none fit, 62 bytes past the decoded buffer. Calif
reported heap disclosure and remote code execution, with application-specific
chains for Keycloak, Jira, Confluence, Artifactory, Jenkins, PingFederate,
Kafka, Solr, Elasticsearch, Gerrit and Spinnaker. Fixed builds are
17.0.21.1, 21.0.13.1, 25.0.5.1 and 27.0.1.1; Oracle GraalVM EE is fixed in
21.3.20.1.

This detector reports **potential exposure** when an unauthenticated management
endpoint discloses a JVM build inside a published affected range. It does not
send the malformed Base64 trigger, does not claim confirmed exploitability and
does not replace a local runtime inventory.

## Why there is no safe trigger-based remote check

The fix, JDK-8393212, adds a four-line guard to the intrinsic's
final-fragment path: a padded tail shorter than one complete block is left to
the Java implementation. The Java-level `Base64.Decoder` rejects the malformed
input with `IllegalArgumentException` both before and after the fix; the only
difference is the out-of-bounds write itself. A remote trigger therefore has no
deterministic response to observe.

Exploitation additionally requires all of the following, none of which is
observable from a network request:

- an affected JVM build;
- an x86-64 CPU exposing `avx512f`, `avx512bw`, `avx512vbmi` and `bmi2`;
- `UseBASE64Intrinsics` enabled (the default when `UseAVX > 2`);
- a C2-compiled Base64 decoder;
- attacker-controlled Base64 reaching `java.util.Base64`;
- application-specific heap grooming.

Sending the malformed tail to an arbitrary endpoint is a crash probe, not a
detection: a crash is not proof of this bug, and the probe is destructive.
Version-only evidence is also incomplete: it cannot establish the CPU, the
effective JVM flags, the JIT state, vendor backports or the decode path. The
finding is therefore explicitly labelled potential exposure.

## Detection contract

The detector reads one or more same-origin JSON documents without credentials,
cookies, redirects, request bodies or state changes. Each document must match a
product-specific envelope; a bare `jvm.version` field is not enough.

| Product | Path | Required evidence |
| --- | --- | --- |
| Spring Boot Actuator | `/actuator/env`, `/env` | `propertySources` or `systemProperties` with `java.runtime.version` / `java.version` |
| Apache Solr | `/solr/admin/info/system?wt=json` | `responseHeader` object and `jvm.version` string |
| Elasticsearch / OpenSearch | `/_nodes/_local` | `cluster_name`, a node `name`, and `jvm.version` |
| Java JMX HTTP adapter | `/jmx?qry=java.lang:type=Runtime` | a bean named `java.lang:type=Runtime` with `VmVersion` |
| Jolokia | `/jolokia/read/java.lang:type=Runtime/VmVersion`, `/actuator/jolokia/...` | `request.mbean`, `request.attribute`, `status == 200`, `value` |

The detector interleaves the target's path prefix and the origin-absolute
paths for each product, stops after the first unambiguous affected build, and
bounds the whole probe to 12 seconds. Each response is capped at 256 KiB and a single request
times out at 2.5 seconds. Duplicate JSON keys, malformed JSON, redirects,
non-200 responses, early-access/beta/preview/snapshot builds and conflicting
versions across property sources are inconclusive and never reported.

Affected ranges:

- Java 17: `17.0.6 <= version < 17.0.21.1`
- Java 21: `21.0.0 <= version < 21.0.13.1`
- Java 25: `25.0.0 <= version < 25.0.5.1`
- Java 27: `27.0.0 <= version < 27.0.1.1`
- Oracle GraalVM EE: `21.3.20.0.3 <= version < 21.3.20.1`

Not reported: standard Java 8 and Java 11 (no vulnerable decoder); Java
17.0.0–17.0.5; Java 18–20, 22–24 and 26 (outside the published risk matrix and
without published fixed builds); Oracle's 8u511b33-perf performance build (a
generic `1.8.0`/`8u` string cannot distinguish it from standard Java 8); and
any version whose only evidence is an HTTP `Server` or `X-Powered-By` header.

## Validation

### Mocked product matrix

`tests/exploits/cve_2026_114938_test.py` covers 52 cases: each product's
affected build, vendor build suffixes (`17.0.21+9-LTS`, `17.0.21.0.3`,
`21.3.20.0.3`), fixed boundaries, Java 11 / 17.0.5 / Java 8, early-access
builds, generic and malformed envelopes, duplicate keys, oversized bodies,
401/403/404/500/302 responses, conflicting versions and a non-HTTP target.

### Loopback fixture

`artifacts/asteroid/2026-11-18-java4shell-runtime-exposure/` in the shared
memory repository contains a stdlib fixture server, a separate network client
that imports the registered detector, and an independent oracle. Result:
**TP 5 / TN 6 / FP 0 / FN 0 / inconclusive 0** across Solr, Actuator,
Elasticsearch, JMX and Jolokia vulnerable cases plus fixed, Java 11,
early-access, generic-lookalike, protected and 404 controls.

### Real Solr

Solr 9.11.0 was run on loopback with two real runtimes:

- Temurin 17.0.21+9: `/solr/admin/info/system?wt=json` returned
  `jvm.version = "17.0.21 17.0.21+9"`; the detector reported one potential
  exposure inside the Java 17 range. TP.
- Temurin 11.0.33+10: the same endpoint returned `11.0.33 11.0.33+10`; the
  detector reported nothing. TN.

A fixed 17.0.21.1 build was not available from the vendor mirror in this
environment, so the fixed boundary is covered by the loopback fixture.

## Limitations

- A management endpoint that is protected, removed, moved under an unknown
  prefix, or returns an unsupported shape is not reported.
- The version may belong to a different JVM than the one processing
  application traffic; different services on the same host can run different
  runtimes.
- Vendor backports can report an older upstream version while already patched,
  and a fixed version does not rule out a second hidden JVM.
- The CPU, effective `UseBASE64Intrinsics` / `UseAVX`, C2 state and the
  attacker-controlled Base64 path are not verified.
- A clean result does not prove the target is patched.
