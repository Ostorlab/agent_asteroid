# CVE-2026-134249: SiYuan loopback-proxy forwarded-header authentication bypass

**[CVE-2026-134249](https://nvd.nist.gov/vuln/detail/CVE-2026-134249) is an
authentication bypass** in SiYuan before 3.8.10 (CWE-287, CVSS 3.1 7.5
`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`). The kernel configures Gin to trust
`127.0.0.1` and `::1` as proxies. In the no-password branch of
`kernel/model/session.go`, it granted the Administrator role when the immediate
TCP peer and the Gin-derived client address both resolved to loopback
addresses, and when the request Host, Origin and X-Forwarded-Host also passed
the local checks.

A SiYuan kernel behind a loopback reverse proxy that preserves a
caller-supplied `X-Forwarded-For` therefore treated an unauthenticated remote
request carrying `Host: localhost:<port>` and `X-Forwarded-For: 127.0.0.1` as a
local administrator. The advisory demonstrates the resulting read of private
note history through `/history/*path` when no lock-screen password is set.

**Affected:** SiYuan before 3.8.10
([GHSA-gmcm-mggw-8759](https://github.com/siyuan-note/siyuan/security/advisories/GHSA-gmcm-mggw-8759))

**Fixed:** SiYuan 3.8.10
([fix commit f951019](https://github.com/siyuan-note/siyuan/commit/f951019168faf035b36c98f8e672719d511881ac),
[release v3.8.10](https://github.com/siyuan-note/siyuan/releases/tag/v3.8.10)).
The fix refuses local trust whenever a third-party forwarded header is present
(`X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Real-IP` or
`Forwarded`); the built-in fixed-port proxy marks its own requests with an
in-process token.

**Severity:** CVSS 3.1 7.5 (High) —
`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`

## How does the detector verify the bypass?

1. `GET /api/system/version` must return SiYuan's exact public release
   document (`{"code":0,"msg":"","data":"<release>"}`). The detector parses a
   stable numeric `x.y.z` release and excludes 3.8.10 and later.
2. A second product marker must corroborate the kernel. Prefer the landing
   redirect to `/stage/build/desktop/` (or the desktop document with its
   SiYuan title and the desktop UI markers whose class prefix is `b3`). When
   the landing is refused, accept the public `/api/system/bootProgress`
   document carrying the same release.
3. `POST /api/notebook/lsNotebooks` is sent twice with the same
   `Host: localhost:<port>` and an anonymous JSON body. The first request sets
   `X-Forwarded-For: 127.0.0.1`; the second sets
   `X-Forwarded-For: 198.51.100.7`, a documentation-range address that is never
   a trusted local client.

A vulnerable kernel reached through a loopback proxy returns HTTP 200 with the
authenticated notebook-list contract for the loopback value, and its own JSON
401 (`code: -1`, an authentication message) for the public value. A fixed
kernel returns 401 for both. A directly exposed vulnerable kernel also returns
401 for both, because the immediate peer is not loopback. A proxy that
overwrites `X-Forwarded-For` with the real client address also returns 401 for
both, and is not reported.

Only the presence of the notebook-list contract and the notebook count are
retained. The probe reads no notebook name, note, history file, token, cookie
or credential, and sends no credential or mutation. The finding confirms the
authentication bypass; it does not claim that a specific private note or
history file was read.

## What does a positive finding claim?

**The finding confirms that the target treated a remotely supplied loopback
`X-Forwarded-For` value as a local administrator.** The two requests differ
only in that header, and only the loopback value was answered with the
authenticated notebook-list contract. That proves the kernel derived local
administrator access from the caller-controlled address.

The finding does not claim that the advisory's note-history read was performed.
It also does not claim that every deployment of the affected release is
vulnerable: the deployment must be reached through a loopback reverse proxy
that preserves the caller-supplied forwarded header and must not have a
lock-screen password set.

## What does the detector miss?

**The detector does not report a deployment when it cannot observe the
differential.** The enumerated cases are:

- A SiYuan kernel behind a non-loopback proxy, or exposed directly, sees the
  scanner's real address as the immediate peer and refuses the loopback value;
  it is not reported even when the code is affected.
- A reverse proxy that overwrites `X-Forwarded-For` with `$remote_addr` (the
  recommended configuration) refuses the loopback value, so the deployment is
  not reported.
- A lock-screen password causes the notebook-list read to require
  authentication even for a locally treated request, so the deployment is not
  reported.
- A proxy that strips every forwarded header answers both requests alike, so
  the control request is not answered with SiYuan's own JSON 401 and the
  deployment is not reported.
- A customized product that does not serve the SiYuan release document, the
  desktop landing or the boot-progress document is not attributed.
- A non-standard API prefix is probed under the scan target's path only.
- A pre-release version label (`3.8.10-alpha.1`) is inconclusive and is not
  reported; no affected range is inferred from it.
- Network errors, timeouts, redirects, oversized bodies and malformed JSON are
  inconclusive and produce no finding; a missing finding is not proof that the
  bypass is absent.

## How do I run the check?

```sh
oxo scan run --install --agent agent/ostorlab/asteroid \
  --arg 'custom_cve_list:["CVE-2026-134249"]' ip 10.0.0.10
```

SiYuan listens on port 6806 by default; adjust the port if the deployment
differs. The equivalent manual differential against a SiYuan deployment behind
a loopback reverse proxy is:

```sh
# Attribution: the public release document and the desktop landing.
curl -i 'http://10.0.0.10/api/system/version'
curl -i 'http://10.0.0.10/'

# Loopback forwarded address: vulnerable kernels answer the notebook contract.
curl -i -X POST 'http://10.0.0.10/api/notebook/lsNotebooks' \
  -H 'Host: localhost:6806' \
  -H 'X-Forwarded-For: 127.0.0.1' \
  -H 'Content-Type: application/json' --data '{}'

# Public forwarded address: the app must refuse with its own 401.
curl -i -X POST 'http://10.0.0.10/api/notebook/lsNotebooks' \
  -H 'Host: localhost:6806' \
  -H 'X-Forwarded-For: 198.51.100.7' \
  -H 'Content-Type: application/json' --data '{}'
```

| Request | Vulnerable before 3.8.10 through a loopback proxy | Fixed 3.8.10 through a loopback proxy |
| --- | --- | --- |
| `GET /api/system/version` | `200`, release below 3.8.10 | `200`, release 3.8.10 or later |
| notebook read, `127.0.0.1` | `200`, notebook-list contract | `401`, authentication refusal |
| notebook read, `198.51.100.7` | `401`, authentication refusal | `401`, authentication refusal |

A directly exposed kernel can report any release below 3.8.10; it still
answers 401 to both notebook reads, so the release alone does not make it
exploitable.

A deployment that answers the loopback request with 401 may be fixed, may not
be behind a loopback proxy, may rewrite the forwarded header, or may have a
lock-screen password; treat that result as inconclusive rather than clean.

## How do I fix CVE-2026-134249?

1. Upgrade SiYuan to 3.8.10 or later, then restart the kernel.
2. Set a non-empty lock-screen password on any kernel reachable through a
   reverse proxy, and keep the kernel bound to loopback or a protected
   management network.
3. Configure the reverse proxy to replace, not pass through, caller-supplied
   forwarded headers. For NGINX use
   `proxy_set_header X-Forwarded-For $remote_addr;` and strip
   `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Real-IP` and `Forwarded`.
4. If an earlier deployment met these preconditions, review access logs for
   requests that combined a loopback `Host` and a loopback `X-Forwarded-For`
   with `/history/`, `/api/notebook/` or other authenticated routes, and treat
   the note history readable by the kernel as potentially disclosed.

## Companion WhatWeb fingerprint

The companion rule lives in `Ostorlab/agent_whatweb` as `plugins/siyuan.rb`
(agent_whatweb 2.0.16). WhatWeb follows the landing redirect to
`/stage/build/desktop/` and matches the `SiYuan` title together with the
desktop `b3` UI markers, so a title-only page and an unrelated product are not
fingerprinted. The release is exposed only by the public
`/api/system/version` API, which WhatWeb does not request at default
aggression, so version extraction is a recorded gap for the inventory.
