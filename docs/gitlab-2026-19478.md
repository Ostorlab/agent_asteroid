# CVE-2026-19478: GitLab GraphQL @gl_introduced directive bypass

**CVE-2026-19478** affects GitLab CE/EE (CWE-94, CVSS 3.1 9.4). GitLab
mis-handles the `@gl_introduced` GraphQL directive, which is meant to gate a
field behind a minimum client version. Attaching the directive with a future
version (`999.0.0`) to a field that should be blocked for unauthenticated
callers lets the query reach it anyway; under certain conditions this same
bypass allows an unauthenticated user to remotely modify or delete public
projects and user data.

**Affected:** GitLab CE/EE 18.2 before 18.11.11, 19.0 before 19.0.8, 19.1
before 19.1.6, 19.2 before 19.2.4

**Fixed:** 18.11.11, 19.0.8, 19.1.6, 19.2.4

**Severity:** CVSS 3.1 9.4 (Critical) — `AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:H/A:H`

## How does the detector verify it?

```
GET  /api/v4/projects?visibility=public&per_page=1
POST /api/graphql
     {"query":"query { project(fullPath: \"<path>\") { name touch @gl_introduced(version: \"999.0.0\") } }"}
```

The check lists one public project anonymously, then queries that project's
`touch` field gated behind `@gl_introduced`, and requires HTTP 200 with
`touch: true` in the response (and no "doesn't exist on type" error). Only
read access to already-public project metadata is exercised — **no mutation
is sent**. No credential or cookie is used and redirects are not followed.

**Limitation:** the check requires at least one public project to exist; a
GitLab instance with no public projects produces no match and is not
reported.

## Remediation

Upgrade GitLab to 18.11.11, 19.0.8, 19.1.6, 19.2.4 or later, which fix the
`@gl_introduced` directive's authorization check.
